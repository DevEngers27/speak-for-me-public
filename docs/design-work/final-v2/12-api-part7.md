# 12 · 后端函数目录（part7）：cron、运维、隐私与 seed

全部是 internal 函数，只经调度器、cron 或 CLI（部署 admin 权限）调用。**每个房间一个 mutation**（03 §3.3.1）：巡检类 cron 先列出目标 id，再逐个 `runAfter(0)` 扇出到同一函数的单房间形态，避免一个巡检事务与所有房间的活动冲突。可选参数只表达"缺省 = 扇出 / 默认值"，不表达删除（B12）。

## 12.20 cron、运维、隐私与 seed

| 函数 | 类型 · 层级 | args → returns | 行为 |
| --- | --- | --- | --- |
| `clock.rollLocalDate` | sysMutation · cron 每小时（UTC :01）· 全部层级 | `{ roomId: v.optional(v.id("rooms")) }` → `v.null()` | 09 §9.6.7：无 `roomId` 时遍历 `rooms.by_status = open`，对 `todayInTimeZone(now, timeZone) > localDate` 的房间扇出；单房间形态推进 `localDate`（推进本身不递增），若当前 `pending_approval` 提案或 open 请求选项的时间结论翻转（如交付日已过）→ `constraints.bump(cause: "clock", actorUserId: null, sourceRefs: [{ kind: "clock", localDate }])` 走 D06。按 (房间, 日期) 幂等 |
| `humanRequests.expireDue` | sysMutation · cron 每小时（UTC :20） | `{ requestId: v.optional(v.id("humanRequests")) }` → `v.null()` | 无 `requestId` 时读 `humanRequests.by_status_expiresAt`（`open` 且 `expiresAt ≤ now`，每批 100）扇出；单请求形态在 `openRoomTx` 内置 `expired`，其 run 若仍是当前 `needs_input` → `ended_no_agreement`（`request_expired`），事件 `human_request_closed`；创建者的待办由 `rooms.view` 派生（D15，7 天） |
| `ops.livenessSweep` | sysMutation · cron 每 5 分钟；`ops.setDraining(false)` 后立即一次 | `{}` → `{ scheduled: v.number(), stuckAttempts: v.number() }` | 列出 `runs.by_status = negotiating` 的 run 并对每个 `runAfter(0, internal.runs.reconcile, { runId })`；列出 `attempts.by_status_deadline` 中 `running` 且 `deadlineAt + 宽限 < now` 的 attempt，`opsLog("stuck_run")` 并调度看门狗逻辑；未接 Axiom 时顺带计算告警计数（15 §15.6.4）。10 已同名 |
| `ops.setDraining` | sysMutation · 全部层级（含 prod，发布流程需要） | `{ draining: v.boolean(), reason: v.string() }` → `{ draining: v.boolean(), changedAt: v.number() }` | 写 `opsFlags`（唯一写者，单行 `key: "global"`，`changedBy: null`）；`opsLog("draining_set", { draining })`；置 false 时 `runAfter(0, internal.ops.livenessSweep)`，由 reconcile 恢复停泊的回合（10 §10.12.3）。`reason` 只进运维记录（≤ 120 码点），不进产品界面 |
| `ops.configHealth` | sysQuery · 全部层级 | `{}` → `{ tier, clerkIssuerConfigured, anthropicKeyConfigured, agentMode, agentsEnabled, modelFallbacks, draining, configValid, invalidFields }` | 只返回变量名、枚举与布尔，从不返回值；CI 每次部署后调用 |
| `ops.activeAttemptCount` | sysQuery · 全部层级 | `{}` → `{ runningLive: v.number(), runningStub: v.number(), negotiatingRuns: v.number() }` | `attempts.by_status_deadline` 前缀 `eq("running")`（`take(1001)`）按 `provenance` 计数；排空等待 `runningLive === 0`（stub 不受排空约束，D17）。10 已同名 |
| `rooms.forceClose` | sysMutation · 全部层级（经 CLI，部署 admin 人工发起，双人确认） | `{ roomId: v.id("rooms"), reason: v.string() }` → `v.object({ status: v.union(v.literal("closed"), v.literal("unchanged")) })` | 身份消失兜底（04 §4.11、INV-SM-07）：creator 或必需审批人的 Clerk 身份已不可用、房间停在 `setup` / `open` 时，等价 creator 的 `rooms.close`（当前 run → `canceled`、open 请求 → `superseded`），事件 `room_closed { by: 'ops' }`，`opsLog(ctx, 'room_force_closed', { roomId })`（`reason` 是自由文本，不进日志——它只随 CLI 调用记录与双人确认单保存，15 §15.6.2）；`executed` / `closed` → `unchanged`。不是 D15 的任何请求选项，界面没有入口 |
| `ops.metrics` | sysQuery · 全部层级 | `{ sinceMs: v.number(), untilMs: v.number() }` → 指标对象 | 时间窗由 CLI 传入（query 不读时钟）；读 `attempts.by_room` / `by_run`、`runs`、`events`；指标与成本汇总见 15 §15.6–15.7，全部带样本量 `n` |
| `ops.purgeRawOutputs` | sysMutation · cron 每日（UTC 03:10） | `{}` → `{ deleted: v.number(), more: v.boolean() }` | 删除 `rawOutputs.by_expiresAt` 中 `expiresAt ≤ now` 的行（每批 500，`more` 时自调度续跑）；保留期 dev 30 天、prod 7 天（15）。两个删除入口之一（另一个是 `seed.reset`；`privacy.redact` 是覆盖不是删除，§12.23 API-13、11 §11.7） |
| `ops.auditUsers` | sysQuery · 全部层级 | `{}` → `{ duplicateTokenIdentifiers: v.number() }` | 只报告是否存在重复的 `users.tokenIdentifier`（并发首登的极端情况，03 §3.14），不返回任何标识；有重复时人工合并 |
| `ops.checkModelConfig` | sysAction · dev / prod 部署后 | `{}` → `{ ok: v.boolean(), code: v.union(v.string(), v.null()) }` | 10 §10.14.2：`AGENT_MODE = live` 而缺 key → 告警（不静默改用 stub）；`models.retrieve("claude-opus-5-5")` 成功即通过，失败映射为 `model_not_found` / `auth` 并告警 |
| `privacy.redact` | sysMutation · 全部层级（经 CLI，人工发起） | `{ table: v.union(v.literal("users"), v.literal("members"), v.literal("invites"), v.literal("rooms"), v.literal("briefs"), v.literal("approvals")), rowId: v.string(), field: v.string() }` → `v.null()`（`rowId` 经 `normalizeId(table, …)` 校验，`field` 必须在该表的清单内） | 03 §3.16.2：只把 `REDACTABLE_FIELDS`（`users.displayName`、`members.displayName`、`invites.invitedEmail`、`rooms.title`、`briefs.softFields.notes`、`approvals.note`）中的字段覆盖为固定串 `"[redacted]"`，同事务写 `pii_redacted{ table, field }`；编译期断言该清单与 `termsKey` 覆盖字段不相交，抹除永不改变任何审批绑定或执行键。只追加表上第二种、也是最后一种允许的写入 |
| `seed.fromFixture` | sysMutation · dev / preview / test | `{ fixtureKey: v.optional(v.string()), stopBeforeRole: v.optional(v.union(roleV, v.null())) }` → `{ roomId: v.id("rooms") }` | 缺省为主 fixture 与 `null`，使 `--preview-run seed:fromFixture` 能以 `{}` 调用。`assertTier`；fixture 经 Zod 加载器校验，金丝雀变体先过 `lintCanaries`；身份：有 `E2E_*_SUBJECT` 时拼 `tokenIdentifier = <issuer>\|<subject>` 并确保 `users` 行，否则用合成身份；用与生产相同的入口逻辑、按 fixture 角色显式传 actor，依次执行 `rooms.create → invites.create + invites.accept → ledger.recordBaseline → catalog.confirm → briefs.confirm ×3`（等价于 canon D18 所说的以 `--identity` 伪造三身份调用公开 mutation，§12.25 Q14）；`stopBeforeRole` 那一方不确认（留给人在演示现场确认）；全部行 `provenance: "seeded"`；第三份确认按生产路径 `openIfReady` 并自动开 run；seed 自身从不写提案 / 审批 / 执行。整体一个事务，非幂等（每次新房间）。**终止状态**（completeness-24）：缺省 `stopBeforeRole: null` → 返回时房间 `open`、cv 1、run 1 已由第三份确认在同一事务内开始（`run_started{ cause: "room_opened" }`，首个 provider 回合已调度；preview / 缺省 dev 为 stub，之后的回合按调度继续推进、产物标 `stub`，E2E 以"run 1 已开始"为起点并按事件等待目标状态）；`stopBeforeRole = r` → 房间停在 `setup`、`r` 的简报未确认、没有 run。canon D18 的"停在三份简报已确认、首个 run 即将开始之前"不可达（第三份确认与开 run 同事务，04 M2），已列 canon_objections（§12.25 Q17） |
| `seed.reset` | sysMutation · dev / preview / test | `{ confirmDeployment: v.string(), fixtureKey: v.union(v.string(), v.null()) }` → `{ roomsDeleted, rowsDeleted, more }` | `await assertTier(["dev","preview","test"], { confirmDeployment })`（部署名取自 `(await ctx.meta.getDeploymentMetadata()).name`，convex-test 中为 `"test"`）；只删 `provenance !== "live"` 的房间及其按 `by_room*` 索引找到的子行，每次 ≤ 2,000 个文档（默认写入限额 16,000 的 8 倍余量，L1 用 `transactionLimits: true` 验证），`more` 时由调用方重复调用；`opsLog("seed_reset", { rooms, rows })`；被删房间的在途 attempt 在守卫处读到缺失文档即按 `stale` 空操作 |

- 生产部署照常包含 `seed.*`（可调用函数集合在部署时确定，不能按环境变量条件导出），由 `assertTier` 在入口拒绝；`rooms.close` 是生产唯一的"清理"。CLI 侧另有 dev-tooling `convex-ops` 守卫（15 §15.9）。
- `ops.*`（含 `ops.setDraining`）是全部层级可用的 internal 函数，dev / preview / test-only 只针对 `seed.*`——canon §1.6 / D17 现文已如此（C53，§12.25 Q5 已关闭）。
