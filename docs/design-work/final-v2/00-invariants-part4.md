### 1.5 执行幂等且原子（核心 5）

| ID | 谓词 | 核心 | 落点 | 违反后果 |
| --- | --- | --- | --- | --- |
| INV-46 | `executions.executionKey = "exec:" + proposalId` 唯一（不含 cv、不哈希、服务端派生）；同一 proposalId 至多一行 `executions`、一行 `changeOrders`、一行 `ledgerEntries(kind: 'commit')`；客户端不传任何幂等键，`requestId` 只用于去重与追溯 | 5 | 索引 `by_executionKey`，`executeIfComplete` 先查后插（命中而守卫却通过 → `internal`，fail closed） | 双执行（C23、X14）；客户端 operationId 两次点击两条 execution（inputs/05 B2） |
| INV-47 | 最后一个必需 approve 的 `approvals` 行 + `executions` + `ledgerEntries(commit)` + `changeOrders` + `tasks` + `events` + `proposal → executed` + `run → executed` + `room → executed` 在同一个 mutation 事务内提交；任一失败全部回滚（不存在"审批已记录执行丢失"或"执行了一半"） | 5 | `approvals.record` 尾部调用 `executeIfComplete`；无 action、无 scheduler 中转 | C12 悬空状态；需要"重试执行"按钮 |
| INV-48 | 执行前在同一事务内重读 `rooms`、`runs`、`proposals`、全部 `approvals.by_proposal` 区间、`members`、`ledgerEntries.by_room` 区间、当前 confirmed `catalogItems`、三方简报硬字段；`isExecutable` 重算；不信任入参、不信任任何缓存的 `committedCents` | 5,4 | `executeIfComplete`；读写 `rooms` 使并发 `budget.setCap` 冲突 | 旧预算上执行（C5、X13） |
| INV-49 | `tasks.taskKey = ${executionId}:${itemKey}:${templateIndex}` 唯一；`tasks` 来自 `proposals.plannedTasks[]` 快照（插入时由当时的 `taskTemplates` 派生），执行时不重算模板；`deriveExecution` 对同输入稳定 | 5 | 索引 `tasks.by_taskKey`；`insertProposal` 快照；SP-I11 | 重复任务；"所见非所写"（idempotent r02） |
| INV-50 | `committedCents = Σ ledgerEntries.amountCents`（`baseline` + `commit`），不存计数器；每房间恰一行 `kind: 'baseline'`（`ledger.recordBaseline` 在 `setup` 阶段写入一次，可为 0，`startFollowUp` 预填但须 finance 确认；finance 上限已确认时要求 `baseline ≤ capCents`，否则 `budget.below_committed`，canon D23 对称守卫）；`commit` 行只由 `executeIfComplete` 写；`executions.committedBeforeCents / committedAfterCents` 是不可变快照只用于展示；对账 R1–R11（finance 候选 08 §10）在每个 convex-test 场景 `afterEach` 断言 | 5,4 | `ledger.recordBaseline` → 已有 baseline 则 `run.invalid_state{ guard: 'baseline_exists' }`；`ledgerEntries` 只追加 | 账不平；第二真相源；setup 期"先定上限、后录更大基线"使 committed > cap |
| INV-51 | mutation 内无外部副作用；执行事务不 `runAfter` 任何 action；通知 / 外部集成只能在提交后经 outbox（17，v1 不建） | 5,7 | Convex 确定性约束 + 结构测试 | OCC 重试重复发通知（C9） |
| INV-52 | 一房一执行：`room.status === 'executed'` 为终态，协商 / 约束 / 成员类写 mutation（含 `budget.setCap` / `catalog.*` / `briefs.confirm` / `ledger.recordBaseline` / `sharedFacts.add` / `invites.*` / `runs.*` / `humanRequests.answer` / `rooms.close`）与内部入口（`constraints.bump` / `startRunTx` / `turns.beginAttempt`）拒绝 `run.invalid_state{ guard: 'room_status' }`，`approvals.record` 按 INV-31（approve 幂等返回 `executed{ alreadyExecuted: true }`、reject / withdraw → `approval.already_executed`）；只有 `tasks.markDone` 与 `rooms.startFollowUp` 放行；后续变更只能 `rooms.startFollowUp({ executionId })` 创建 `followsExecutionId` 指向旧执行的新房间（经 `addMember` 预分配同三席、只把**未交付**的目录行——`itemKey ∉` 旧执行 `terms.itemKeys`——复制为 `draft`、基线预填旧 `committedAfterCents`）；因此不存在"同房间再次承诺已执行范围"。跨房间：后续房间的目录与任何候选快照永不含已交付条目，后续房间对已交付键调 `catalog.confirm` → `item.duplicate`（canon D04、12 §12.6 / §12.12） | 5,7 | `openRoomTx` 的 `allow` 默认不含 `executed`（04 §4.2.2、12 §12.2 第 10 条）；`rooms.startFollowUp` | 重复承诺已执行范围（inputs/07 第六类 + candidates1 判词 ×6） |
| INV-53 | 执行**不**递增 cv；执行后 `executions.approvalIds[]` 冻结当时的 approvals 行 id，结果页与变更单只读快照，后续任何展示不派生 stale | 5,6 | `executeIfComplete`；结构测试"执行路径不调用 `constraints.bump`" | 已执行审批显示 "Invalidated by constraints v5"（C4、inputs/07 第五类） |
