# 01 产品（事件溯源候选）

## 1. 用户与角色

| 角色 | 是谁（首个场景的组织假设） | 私密委托给代理的内容 | 必须亲自做的事 |
| --- | --- | --- | --- |
| customer | 中型客户的项目负责人 | 必需/期望/可延后范围、硬截止日、首选日期（私密） | 确认简报、回答取舍请求、签核条款（Accept terms） |
| provider | 外包工作室负责人 | 已确认报价目录（确认即对房间公开）、最早开工日、私密备注 | 确认/改价报价、签核条款、完成任务 |
| finance | 客户方独立预算负责人 | 预算上限（买方可见、provider 不可见）、审批备注 | 设定/调整预算（必须写原因）、批准预算承诺（Approve budget commitment） |
| owner | 建房的人（通常是 customer） | — | 建房、发邀请、关闭房间；不因此获得审批权 |

假设（hypothesis，非事实）：小企业里 finance 常由项目负责人兼任；服务商愿意进入客户工作区的动机未验证（F01.4）。v1 要求三个角色是三个不同账号。

## 2. 首个场景

软件服务范围变更：在已有 $4,000 承诺、$5,000 总预算下，就一组变更条目（SSO 登录改造、使用报表、CSV 导出）的范围、报价、交付日达成三方一致，执行后写入变更单、预算承诺与任务。核心转折：审批途中预算降到 $4,800，旧方案自动失效，系统重谈或向具体的人请求取舍（完整走查见 14）。全部示例数字标注 Simulated。

## 3. 为什么需要三个代理（LLM 的职责边界）

代码负责：可行组合枚举、金额、日期、预算、权限、状态、审批完成判定。代理负责：
1. 在候选中为委托人选择并解释（只给委托人看的 rationale）；
2. 代表委托人还价（counter 到另一个候选）、表达拒绝理由（reasonCode）；
3. 发现需要人来决定的点（clarify / NEEDS_TRADEOFF），由代码把问题结构化后交给具体的人。
产品叙述如实写成："三个相互隔离的代理各自调用模型；所有算术、校验与执行由确定性代码完成；代理的建议永远不是批准。"

## 4. 做什么 / 不做什么

| 做 | 不做 |
| --- | --- |
| 私密简报、逐项披露、按角色裁剪的实时视图 | 把私密字段发到浏览器再隐藏 |
| 代理协商（候选内选择、还价、澄清） | 让模型给出金额、条目、日期 |
| 人对具体版本审批；约束变更自动失效 | 把代理"建议接受"当成批准 |
| 原子幂等写入变更单、承诺、任务 | 转账、签署有法律效力的合同、改外部 ERP |
| 不可篡改的事件历史、追溯"结果怎么来的"、约束历史 | 删除或改写历史（唯一例外：整房间的合规删除） |
| 模拟数据处处标注；缺信息时向具体的人请求 | 编造一致意见、伪装预跑结果为现场生成 |

## 5. 关键用户旅程

| # | 旅程 | 步骤（谁 → 做什么 → 看到什么） |
| --- | --- | --- |
| J1 | 建房与加入 | owner 建房 → 拿到三个一次性邀请链接 → 各方登录接受 → 席位绑定账号 |
| J2 | 私密简报 | 各方填写结构化简报 → 勾选对他方可见的字段 → 预览"房间能看到什么" → 确认（成为不可变版本） |
| J3 | 协商 | 最后一份简报确认后 run 自动开始 → 工作台显示各代理回合状态 → 提案卡出现（来源、金额、交付日、检查清单） |
| J4 | 审批 | 每方对提案 v{n} 点 "Accept terms" / "Approve budget commitment" → 最后一票即执行 → 结果页出现变更单与任务 |
| J5 | 约束变更 | finance 下调预算并写原因 → 三个窗口同一刻看到旧提案 Blocked、旧审批 stale → 新 run 自动开始 |
| J6 | 取舍 | 代码判定需要人 → 目标角色看到选项卡（如"$800 晚一周 vs $550 按时但不含报表"）→ 选择 → 进入审批 |
| J7 | 追溯 | 任何人在结果页点 "How we got here" → 看到从变更单回到预算变更、提案、回合与审批的事件链（按角色裁剪） |
| J8 | 失败恢复 | 回合超时/失败 → "Retry turn" → 继续；迟到结果被丢弃并在时间线说明 |
