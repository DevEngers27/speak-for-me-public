# 01 产品

## 1. 用户与角色（首个场景）

| 角色 | 是谁（假设，F01.4） | 私密交给代理的 | 对房间披露的（自选） | 要做的决定 |
| --- | --- | --- | --- | --- |
| customer | 客户方项目负责人 | 必需条目、想要条目、硬截止日、偏好日期、备注 | 必需/想要条目、截止日 | 接受条款；取舍（延后哪项、选哪个方案） |
| provider | 外包工作室负责人 | 报价目录（确认即公开）、偏好条目、备注 | 报价目录 | 接受条款；完成任务 |
| finance | 客户方预算负责人 | 预算上限、已有承诺、备注 | 预算两项（只能给 customer） | 批准预算承诺；是否加预算 |

一个人在一个房间只占一个角色；角色由邀请决定。房主没有额外审批权。

## 2. 为什么需要 LLM 代理（F01.1 的回答）

代码已经能算金额、判断硬约束、枚举组合。LLM 做代码做不了或不该做的三件事：
1. **在不知道对方底线的情况下提议与还价**：provider 代理只看到公开约束与反馈，决定先提什么、被挡后怎么让步；
2. **代表本方评估软偏好**：customer/finance 代理按私密偏好与备注决定建议接受还是拒绝，并给本人写理由；
3. **知道何时该问自己的委托人**（clarify）。
"无解"、"轮次用尽"由代码判定并生成向具体人的问题。finance 代理只评估与解释，不做算术；三个代理是三次独立调用，从不共享一个上下文。

## 3. 系统做什么 / 不做什么

| 做 | 不做 |
| --- | --- |
| 私密简报 + 逐项披露 | 把任何私密字段发到他人浏览器再隐藏 |
| 代理提议、还价、澄清、建议接受、拒绝 | 代理批准或执行 |
| 代码校验金额、范围、日期、预算、来源 | 让模型给出金额或日期 |
| 人对具体版本批准；全部到齐后原子执行 | 转账、签署合同、修改外部 ERP |
| 写变更单、预算承诺快照、任务 | 对外部系统宣称 exactly-once |
| 约束变化让旧方案与旧审批失效并重谈或问人 | 删除或改写历史 |
| 标注所有模拟数据与 stub 代理产物 | 编造一致意见、预跑结果不标注 |

## 4. 关键用户旅程

1. **建房与邀请**：customer 创建房间（选自己角色）→ 得到 provider、finance 两个一次性邀请链接 → 发给对方 → 对方登录认领。
2. **填简报**：每人在"我的简报"页填结构化字段，逐项勾选披露，看到"房间能看到什么"预览，确认。第三份确认后自动开始协商。
3. **看协商**：工作台显示当前 run、每个代理回合状态（"Provider agent drafting…"）、每个提案的条款、可执行性与原因（按角色措辞）。本人可展开自己代理的理由。
4. **批准**：提案进入待批后，三人各自点按钮（"Accept terms" / "Approve budget commitment"），按钮上写明版本号；代理的"建议接受"旁写 "Agent recommendation — not an approval"。
5. **约束变化**：finance 降预算（带原因）→ 所有窗口同时显示旧提案被取代、旧审批失效 → 新协商自动开始，或问题卡片出现在相关的人面前。
6. **取舍**：被点名的人在"需要你决定"区看到代码生成的选项，点一个即生效；先回答者生效，其他问题自动作废。
7. **结果**：执行后结果页显示变更单（内部记录声明）、任务、预算影响（仅买方）、审批记录，可追溯到每个来源版本。
8. **后续变更**：执行后可以开新一轮协商延后的条目，形成新的变更单。

## 5. 成功标准（参数化，F01.3）

- For any stored budget, a proposal is executable only if `priorCommitted + executed + amount ≤ total`；降低上限使旧方案即时阻断，并开始重谈或请求人。
- 任何经 UI 输入的预算、报价、截止日在提交后 1 秒内（订阅回推）得到正确的可执行性。
- provider 的所有 query 返回与代理上下文中不出现 finance 的数值（canary 测试）。
