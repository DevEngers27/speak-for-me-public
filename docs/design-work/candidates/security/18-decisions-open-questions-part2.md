# 18 决策记录与开放问题（part2：ADR-12 至 ADR-22、输入冲突裁决、开放问题、待验证）

### ADR-12 用户表 + 一次性席位 + 哈希邀请；一人一席；席位不可解绑（v1）
- 背景：R 没有邀请设计（GAP-17）；"知道 roomId 就能自选 finance"与"一人三席"是最直接的越权（F07.9）；F03.2 的邀请码明文存储。
- 决定：`users` 以 `tokenIdentifier` 为键；建房时一次性插入全部席位；邀请令牌 256 位、只存 SHA-256、72 h、一次性；`accept` 内检查一人一席；v1 不支持解绑。
- 后果：错人占席只能关房重建（开放问题 Q-3）；令牌生成需要 action（V-6）。

### ADR-13 人工请求完整实体；选项由代码按目标视图生成；并行发给多人
- 背景：F02.7/F05.6 推荐完整版；RA-R13 的三种取舍对应三个角色的权限；RA Q8 顺序还是并行。
- 决定：完整 `humanRequests`；选项是可执行动作（adopt / amend / revise_catalog / disclose / decline）；并行发送，第一个改变约束的回答取消其余取舍请求。
- 后果：可追溯、可取消、绑定 cv；放宽可能需要多步（因为每个目标只按自己的视图计算）。

### ADR-14 类型化安全日志 + 错误码；不保存模型原文与 prompt
- 决定：`logEvent(name, SafeLogFields)` 是唯一日志出口；`ConvexError({ code, params })` 的 params 只含调用者拥有的值；不存原文，只存 `contextDigest` 与结构化结果。
- 后果：调试依赖 stub、`scripts/try-agent.ts` 与结构化字段；无法事后复盘模型"说了什么"，这是有意的（P-12、T-08）。

### ADR-15 三个代理都调用模型，但只做选择与解释
- 背景：F01.1/F10.17 质疑三个代理的必要性。
- 决定：保留三方代理（含 finance）；数字、可行性、升级全部归代码；产品文案为 "three advisory agents + deterministic checks"。
- 后果：finance 代理的价值在于读取 finance 的软信息并解释；若评估显示其建议对结果无影响，可改为纯确定性 finance（开放问题 Q-15）。

### ADR-16 模型与 effort
- 决定：全部调用点默认 `claude-opus-5-5`（平台约束规定未经用户决定不为省钱降级）；协商回合 `medium`、抽取 `low`；不传 thinking 与采样参数；服务端回退待 V-8 验证后再开。
- 后果：成本按 inputs/04 §4.10 估算约每 run $0.35–0.45（5 次回合，待实测）；更小模型作为用户决策选项（Q-1）。

### ADR-17 setup 期不递增 cv；激活 = cv 1；执行也递增 cv
- 理由：setup 期没有可失效的提案与决定；执行改变已承诺额，而已承诺额是规则输入——递增后任何历史求值都可精确重算（03 §3.4）。

### ADR-18 预算上限不得低于已承诺额
- 选项：允许并进入 `needs_input`（F06.3）/ 拒绝（RA-R10）。决定：拒绝（`CAP_BELOW_COMMITTED`）。后果：台账不变量 `committed ≤ cap` 始终成立；现实中的"超额承诺"需要线下处理（Q-16）。

### ADR-19 条款签核与预算承诺只在界面上区分
- 背景：F08.3 建议 approvals 加 `kind: terms | budget`。决定：数据层统一 `approve`，按钮文案由场景按角色给出。后果：完成判定简单；若将来两类签核需要不同规则，再在场景策略中区分。

### ADR-20 房间时区建房后固定；"今天"不进入 cv
- 后果：时间流逝导致的阻断（交付日已过）在执行时重算暴露，不使审批失效；query 中的"今天"只用于显示（06 §6.5）。

### ADR-21 不提供录制回放；seed 停在激活点
- 背景：F15.1 建议阶段快照与"seeded from run"。决定：不做；stub 满足离线与演示。后果：演练要从激活开始实际跑（stub 下数秒）；不可能出现被误认为现场生成的预置结果（核心 8）。

### ADR-22 代理评审结论只对本方可见
- 背景：Role A 的"Agent messages"区与 R 的协商消息对全员展示。决定：他方只看到结构化提案、run 进度与"Reviews complete"；结论与理由只给本方委托人。后果：协商过程对他方不透明，但人的决定（含公开理由码）仍公开（07 §7.9）。

## 18.1 输入之间冲突的裁决记录

| 冲突 | 输入 | 裁决（依据） |
| --- | --- | --- |
| 预算对 customer 是否默认可见 | F07.1 推荐可见 vs R:239 finance 私密 | 默认不可见，需 finance 显式披露（核心 1） |
| 基线放在哪里 | F02.3 baseline commitment vs RA 房间字段 | finance 简报硬字段（ADR-02） |
| 决定 patch 还是追加 | F03.7 patch vs RA 追加 | 追加（核心 6） |
| 是否需要 contentHash | RA 需要 vs F03.7 不需要 | 不需要（提案不可变） |
| 约束变化时 run 的处理 | F04.1 两种写法 | 取代 + 新 run（ADR-10） |
| SDK 重试层数 | F10.4 红队（SDK 2 次）vs 单层原则 | 应用层单层（ADR-11） |
| 模型输出形状 | R Zod / F05.2 判别联合 vs inputs/04 实测 | 手工扁平 schema（ADR-05，以平台事实为准） |
| 必需条目能否"显式延后" | F06.2 整理者建议不能 | 不能；走人工取舍（`MISSING_REQUIRED_ITEM`） |
| priority 放目录还是简报 | P4 vs architecture-09 | customer 简报（required/preferred），目录只描述供给 |
| `messages.parse` 失败语义 | 技能文档"返回 null" vs SDK 1.1.0 源码"抛错" | 以源码为准，改用 `create` + 自行校验 |
