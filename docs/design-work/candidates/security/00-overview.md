# 00 概览（候选设计：安全、隐私与信任边界优先）

## 0.1 这份设计是怎么推出来的

先写威胁模型（07）：私密信息会从哪些路径流向他方（公共文本、代理 prompt、日志、客户端 query、错误信息），他方文本如何劫持本方代理，谁能冒充角色，旧批准如何匹配新内容，执行如何被重复，模型如何"发明"价格，迟到的结果如何覆盖新状态。然后从"每条数据给谁看"出发切表（一表一受众），从"谁能改"出发决定不可变对象，从"模型能输出什么"出发设计协议，最后才写字段、状态机与 API。每个威胁都对应到具体防线与 16 章的测试编号。

## 0.2 设计原则

1. **一表一受众**：每条记录要么全房间可见，要么只属于一个参与方，要么只属于系统；跨受众只允许五条受控投影（07 §7.11）。
2. **模型的输出空间就是安全边界**：模型只能从服务端生成的候选 ID 与枚举中选择，外加一段只回给本方的 rationale；它写不出金额、日期、条目、身份或任何公共文本（05）。
3. **视图决定能力**：代理的候选集、人工请求的选项都只由目标角色"本来就能看到的信息"计算（ADR-07），隐私定义写成可测试的非干扰性质（07 §7.13）。
4. **影响他人判断的对象不可变，能派生的不存**：可追溯来自"不可变 + 确定性重算"，而不是状态字段（02 §2.1）。
5. **两组守卫分开**：审批守卫保护"人看到的就是被批准的"，回合守卫保护"模型结果属于当前协商"（04 §4.9）。
6. **每个组件都说明它解决什么**；两个完整方案选简单的（例如：变更单即执行记录，不另设表；不引入编排组件）。

## 0.3 不可动摇的核心如何被保证

| 核心 | 由哪些设计点保证 | 主要章节 | 关键测试 |
| --- | --- | --- | --- |
| 1 私密委托 | 一表一受众与五条受控投影；逐字段披露写入简报版本、固有披露清单；`buildAgentContext` 唯一入口与 `RoleView` 类型；候选与放宽选项按视图计算；reasonCode 粗化；事件载荷只含公开值、读时渲染；DTO 构造器 + `returns` 校验器；安全日志与错误参数纪律；代理之间无自由文本 | 07、02、03、05、06 | TC-PRIV-01–08、TC-INJ-01/02 |
| 2 代理只建议 | 动作集没有"批准"；`recommend_accept` 只写本方笔记；决定只来自人的 `decisions.decide`；升级给人由代码决定；披露永远由人决定（澄清 = 向人发请求）；界面标注 "only people approve" | 05、08、13 | TC-INJ-03、TC-AUTH-08 |
| 3 人批准具体版本 | 提案不可变；决定绑定 (proposalId, cv)；`expectedConstraintsVersion` 防旧页面批准；必需审批角色与目录版本快照在提案上；cv 唯一入口 `bumpConstraints` 覆盖全部硬约束变化与执行；旧决定 stale 不删除；不复制提案 | 08、09、04 | TC-VER-01–10 |
| 4 代码负责校验 | `evaluate` 纯函数在显示、批准、执行三处共用；价格、日期、延后项只由 `deriveTerms` 从已发布目录计算；来源核对（`CATALOG_STALE`）；全局可行性与无解由代码判定；输入校验单一来源（金额、日期、条目键） | 06、14 | TC-RULE-01–11、TC-INJ-05 |
| 5 执行幂等且原子 | 执行只在最后一票的 `decide` 事务内；run 状态守卫为主、`operationKey` 为辅；变更单、承诺、任务、run 迁移、cv 递增同事务；重复调用返回同一变更单；真实部署并发测试 | 08 | TC-EXE-01–06 |
| 6 历史不可篡改 | 不可变表只有 insert（静态扫描）；决定只追加（撤回也是一行）；每个 cv 一行约束快照；承诺带执行时预算快照；执行递增 cv 使任何历史求值可精确重算；事件只追加 | 03、09 | TC-VER-05/06、TC-EXE-05 |
| 7 执行边界 | 只写变更单、承诺、任务；无任何外部调用入口；界面与打印视图标注内部记录；外部集成只经 outbox 扩展点 | 08、17 | 评审 + API 快照 |
| 8 不伪造 | `isSimulated` 贯穿并传递；stub 代理与真实代理共用流程且标注；不提供录制回放；seed 停在激活点；无解时生成人工请求而不是提案；成本只按 token 估算并标注 | 10、14、15 | TC-OPS-03、TC-RUN-09 |

## 0.4 术语表

| 术语 | 含义 |
| --- | --- |
| 房间 room | 一次需要多方同意的事务；生命周期 setup → active → closed |
| 席位 seat（`participants`） | 房间中的一个角色位置，绑定至多一个用户 |
| 私密简报 brief | 参与方的硬约束、软偏好、备注与披露决定；草稿可变，确认版本不可变 |
| 目录 catalog | provider 发布的公开报价集，版本不可变 |
| 约束版本 cv | 规则求值全部输入的版本；硬约束变化或执行时 +1；决定绑定它 |
| 约束快照 | cv → 当时生效的简报版本与目录版本 |
| run | 固定 cv 下的一次协商尝试；每房间至多一个非终态 run |
| 回合 turn | 一个角色代理的一次调用尝试 |
| 候选 candidate | 服务端在某角色视图中枚举出的可选组合，模型只能按 ID 选择 |
| 提案 proposal | 不可变条款；状态全部派生 |
| 决定 decision | 人对 (提案, cv) 的 approve / reject / withdraw，只追加 |
| 人工请求 | 代码生成、发给具体某人的取舍或披露请求 |
| 变更单 change order | 执行记录本身（冻结条款、所用决定、规则版本） |
| 承诺 commitment | 预算台账条目，带执行时预算快照 |
| 固有披露 | 协作无法避免的派生事实（如"是否满足对方约束"这一位） |
| 受控投影 X1–X5 | 跨受众读取的五个唯一实现函数 |
| `pricingKey` / `termsKey` | 由目录决定的条款键 / 含延后项的可读条款键 |

## 0.5 与原方案的主要差异

| 原方案 | 本设计 | ADR |
| --- | --- | --- |
| 预算放在全员可见的 rooms 上；`committedCents` 计数器 | 预算与基线是 finance 简报硬字段；已承诺 = 基线 + 承诺台账；默认对任何人不披露 | ADR-02、03 |
| 买方默认可见预算（审查推荐） | 必须 finance 显式披露；provider 只见粗类 | ADR-03 |
| 模型输出 scope/金额/sourceRefs/publicSummary（R）或 itemKeys 判别联合（F05.2） | 模型只输出候选 ID 与枚举；手工扁平 schema；公共文本全部模板 | ADR-05、06 |
| clarify 由人或对方代理回答 | 澄清 = 向人发结构化披露请求 | ADR-06 |
| 可行组合由代码用全部信息枚举再交给模型 | 候选与放宽选项只按目标视图计算 | ADR-07 |
| 审批 patch 最新决定 / contentHash | 决定只追加，绑定 (proposalId, cv) + 期望 cv | ADR-08 |
| 独立 executions 表、重发执行按钮 | 变更单即执行记录，只在最后一票事务内产生 | ADR-09 |
| revalidated 提案复制 | 不复制；同一提案重新审批 | ADR-10 |
| 事件 room/private 二元可见、预渲染文本 | 事件全部公开且载荷只含公开值、读时按查看者渲染 | ADR-01 |
| 代理消息对全员展示 | 代理结论与理由只给本方 | ADR-22 |
| 单一 status、paused/failed 未定义 | 房间、run、回合、请求分层状态机；提案与决定状态派生 | 04 |
| 只有改预算递增约束版本（RA） | 全部硬约束变化与执行都经 `bumpConstraints` | ADR-17 |
