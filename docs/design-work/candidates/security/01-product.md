# 01 产品

## 1.1 一句话

Speak for Me 让需要共同同意一件事的几方，各自把目标、底线和偏好私密地交给自己的 AI 代理；代理在代码划定的可行范围内替各自的委托人选择、还价并解释；代码独立判定可行性；只有人能批准一个具体版本；全员批准后系统一次性写入内部执行记录；任何约束变化都会让旧方案和旧批准自动失效。

差异化不是"两个代理对话"，而是这条链条的每一环都可验证：私密委托 → 有边界的代理协商 → 确定性校验 → 版本化的人工批准 → 原子幂等执行 → 约束变化后的恢复（V-08）。

## 1.2 用户与角色

| 角色（首场景） | 典型身份 | 私密交给代理的东西 | 在系统里能做的事 |
| --- | --- | --- | --- |
| customer | 客户方项目负责人 | 请求范围、必需条目、硬截止日、偏好（首选日、偏好条目）、自由备注 | 建房、邀请、确认简报、决定披露、批准、拒绝、回答请求 |
| provider | 外部服务商（通常是另一家公司） | 最低接单额、自由备注（产能、不可接受条款）；报价目录在发布前私有 | 同上 + 发布目录、更新任务状态 |
| finance | 客户方预算负责人 | 预算上限、基线已承诺额及来源、自由备注 | 同上 + 调整预算上限 |

组织形态是产品假设：首场景假定"外包工作室 + 有独立预算负责人的客户"或"企业内部采购"；小企业里财务常常就是项目负责人本人，这种情况下同一个人不能同时占两个席位，需要第二个人（Q-9）。

## 1.3 首个场景

软件服务范围变更：客户想在既有合同之外追加三项工作（登录改造、使用报表、导出），预算已承诺大部分，全部加急交付超预算；协商得到一期方案并获批准前，finance 下调了预算，旧方案被阻断，系统重新协商出新的一期方案，三方批准后写入变更单、预算承诺与任务（14 章）。

## 1.4 系统做什么 / 不做什么

| 做 | 不做 |
| --- | --- |
| 私密保存每方的约束与偏好，只向本人和本人的代理展示 | 端到端加密或"零泄露"承诺；授权的私密上下文会发给模型提供方（P-11） |
| 让参与方逐字段决定向谁披露什么 | 替参与方决定披露；代理不能代为披露 |
| 由代码枚举可行组合、计算价格与日期、判定可执行性与无解 | 让模型给出金额、日期、条目或"是否可行"的结论 |
| 三方代理在本方可接受的候选中选择、还价、解释 | 代理批准、代理签字、代理之间自由对话 |
| 无解或分歧时向具体的人提出可执行的取舍选项 | 伪造一致意见 |
| 人批准具体版本；全员批准后原子写入变更单、承诺、任务 | 转账、电子签名、修改外部 ERP（核心 7） |
| 约束变化时旧批准自动失效、各方同步看到阻断与原因 | 静默沿用旧批准 |
| 保留全部版本与历史，可追溯每个结果 | 删除或改写历史（合规删除走运维流程） |
| 明确标注模拟数据、模拟代理与内部记录 | 把预置或录制结果当作现场结果展示 |

## 1.5 关键用户旅程

**J1 建房与邀请**：customer 新建房间（标题、目标、场景、时区、自选角色）→ 发出 provider、finance 两个一次性邀请链接 → 对方登录后看到"You're invited to join *Analytics portal change request* as Finance owner"→ 接受。房间显示三个席位与显示名。

**J2 私密简报**：每人在简报页填写结构化字段（或粘贴邮件让系统预填，再逐项确认）→ 为每个可披露字段选择受众 → 在 "What others can see" 中看到他方真实可见的内容 → 勾选固有披露说明 → 确认版本。provider 另外编辑并发布报价目录。三方都确认后房间自动激活，协商开始。

**J3 协商**：工作台显示 run 进度（"Provider agent drafting…"）→ 提案卡出现，带确切条款、按我的权限显示的检查结果、与上一版的差异 → 我的代理笔记解释它为什么建议接受或还价 → 无需操作，直到"Your turn"出现。

**J4 批准**：当前提案通过检查后，每个人看到 "Approve change v2 under constraints v1"（provider 为 "Accept terms"，finance 为 "Approve budget commitment"）以及批准后将创建的记录；点击即记录；最后一人批准的同一时刻系统写入变更单、承诺和任务。

**J5 约束变化**：finance 在审批途中把上限从 $5,000 调到 $4,800，填写原因 → 三个窗口同时看到 v2 被阻断：finance 与 customer 看到"Over budget by $100"，provider 看到"Blocked: buyer-side constraint"；已有的批准显示为"no longer applies" → 新一轮协商自动开始，得到 v4（$750，标准交付）→ 三方重新批准 → 执行。

**J6 无解与取舍**：若调到 $4,400，系统判定无任何可行组合，不调用模型，直接分别询问：finance "Raise to at least $4,450?"，customer "Make LOGIN optional?"，provider "Publish a revised catalog?"——每个问题只包含收件人本来就能知道的数字。

**J7 拒绝**：任何人都可以拒绝并选择一个公开理由；拒绝者的代理在下一轮提出替代方案，轮次用尽时拒绝者收到可选的替代方案列表；房间永远不会停在无出路的状态。

**J8 结果与追溯**：结果页显示变更单（"Internal record — not a contract, no payment has been made"）、任务、按角色的预算影响、完整的决定记录（含撤回与过期的批准）和时间线；从变更单可以一路追溯到当时的约束版本与报价版本。

**J9 后续修订**：已执行后，任何成员可以请求重新协商（例如处理延后的 EXPORT），新的变更单叠加在已承诺额上。

## 1.6 成功度量（只在测量后陈述，报告样本数）

- 从激活到第一个可批准提案的时间（目标：正常两轮 ≤ 60 s，待用最终模型实测）。
- 人工干预次数（请求、拒绝、重试）。
- 硬约束违规被执行的次数：必须为 0。
- 隐私金丝雀命中数：必须为 0。
- 每 run 模型调用数与估算成本。
