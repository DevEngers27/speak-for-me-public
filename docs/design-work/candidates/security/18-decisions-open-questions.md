# 18 决策记录与开放问题（part1：ADR-01 至 ADR-11）

> 本章分 2 个文件：part1（本文件）；part2 ADR-12 至 ADR-22、输入冲突的裁决记录、开放问题、待验证事项。
> 每条 ADR：背景 / 选项 / 决定 / 后果。"偏离"注明与原 README（R）、Role A 分支（RA）或审查建议（F）的差异。

### ADR-01 一表一受众；事件全部房间可见且载荷只含公开值
- 背景：原 schema 的事件只有 room/private 二元（GAP-15）；Role A 写入预渲染文本并在浏览器过滤（RA-B20）；审查对"私有事件"口径不一（F07.6）。字段级投影是最容易出错的隐私机制。
- 选项：A 事件带受众判别联合并在 query 内过滤；B 事件全部公开、只放公开值，私密历史来自本就私有的表。
- 决定：B，并把"一表一受众"推广为全部表的原则，跨受众读取只允许五条受控投影（07 §7.11）。
- 后果：隐私审查面从"每个字段"缩小到"五个函数 + R 表新增字段"；本人的私密时间线由前端组合多个私有 query；事件文本按查看者在读时渲染。偏离 R（visibility 字段）、RA（私有事件）。

### ADR-02 预算是 finance 简报中的硬约束；已承诺额 = 基线 + 承诺台账
- 背景：R 把预算放在全员可见的 rooms 上（GAP-01）；`committedCents` 计数器与台账两份真相（F02.3）；基线 $4,000 没有来源（GAP-16）。
- 选项：A 独立 `budgets` 表 + 基线作为一条 commitment；B 预算与基线都是 finance 简报版本的硬字段，台账只记执行产生的承诺。
- 决定：B。
- 后果：改预算就是确认新的 finance 简报版本，与所有其他约束变化同一机制（版本化、快照、cv）；基线由 finance 声明并带来源说明；房间之上的共享预算留作扩展（17 §17.5）。偏离 R、RA（room 上的预算）与 F02.3/F02.4（独立 budgets 表、基线 commitment）。

### ADR-03 显式披露决定写入简报版本；固有披露清单；reasonCode 按查看者粗化
- 背景：核心 1 要求跨方可见内容都经显式决定；F07.1 建议"买方（customer、finance）默认可见预算数字"。
- 选项：A 按买方/卖方默认划分；B 一律默认不披露，由所有者逐字段选择受众，协作必需的派生事实列为固有披露并要求确认。
- 决定：B。fixture 中 finance 把 headroom 披露给 customer，示范而非默认。
- 后果：customer 是否看到预算由 finance 决定，而不是由系统假定"同一采购方"；provider 只看到 `BUYER_CONSTRAINT` 粗类；每个提案泄露 1 位可行性被明确接受并告知（07 §7.5）。偏离 F07.1 的推荐方案。

### ADR-04 发布目录即披露；目录版本不可变；提案绑定目录版本
- 背景：RA-D07 把报价作为结构化记录，但"何时从私密变公开"只在 UI 层成立（RA-B24）；改价后旧提案仍可执行（RA-B04）。
- 决定：provider 的草稿目录私有；"发布"是显式披露动作，产生不可变版本并递增 cv；提案记录 `catalogVersionId`，旧版本被取代即 `CATALOG_STALE`。
- 后果：同价重新发布也会让旧提案失效并需重新提出——审批永远对应它看到的那份报价。v1 没有"只给本方代理用的私有报价"（开放问题 Q-14）。

### ADR-05 模型只输出候选 ID 与枚举；输出 schema 手工生成，不用联合与 null
- 背景：R 的 Zod 契约让模型给出 scope、金额与 sourceRefs（GAP-04/07，F02.1）；F05.2 建议模型输出 itemKeys 的判别联合；inputs/04 实测 `zodOutputFormat` 把 enum/const 降为描述，根级 anyOf 与可空类型的接受情况待验证。
- 选项：A Zod 判别联合 + itemKeys；B 服务端按回合生成只含 object/string/enum 的扁平 schema，候选 ID 与理由码都是枚举，"不适用"用 `"NONE"`。
- 决定：B，解码后仍用 Zod + 语义校验。
- 后果：模型无法表达任何金额、日期、条目键；结构化输出的约束只依赖确定受支持的子集；代价是每回合 schema 不同（首次编译开销，结构固定、枚举值不同，缓存行为待验证）。偏离 R 与 F05.2。

### ADR-06 代理之间没有自由文本；rationale 只给本方；澄清 = 向人发结构化披露请求
- 背景：R 的 `publicSummary` 是必填自由文本（GAP-06）；clarify 由谁回答未定（GAP-11）；代理答复他方问题本质上是未经人决定的披露，也是注入通道。
- 决定：对他方可见的文本全部来自模板；模型文本只写入 `agentNotes`；`clarifyTarget` 生成发给目标**人**的披露请求，非阻塞。
- 后果：跨代理注入只能经由他方撰写的短文本（标题、目标）进入，且无法跨边界写出；协商记录对他方不透明（只见结构化提案与状态）。偏离 R（publicSummary、clarify 动作语义）。

### ADR-07 候选集与放宽选项都由目标角色的视图计算
- 背景：F05.5/F06.5 建议"代码枚举可行组合、模型在候选中挑"；若用全部私密数据枚举，再把候选交给 provider 代理，候选集本身就泄露了预算区间。
- 决定：`enumerateCandidates` 与 `relaxations` 只接收角色视图输入（未知字段的检查被跳过）；全局可行性只以"有/无"影响流程。
- 后果：provider 可能提出超预算的方案（它确实不知道预算），由买方代理还价——这正是协商；人工请求里的数字只可能是目标人本来就能推出的值。新增决定，审查未覆盖。

### ADR-08 决定只追加，绑定 (proposalId, cv)，并要求调用者携带期望 cv
- 背景：R 只存版本号（F08.1）；F03.7 建议同 (proposal, user) patch 最新决定；RA 建议 contentHash。
- 决定：只追加（撤回也是一行）；当前决定读时派生；不另算内容哈希（提案不可变，id 即内容）；`expectedConstraintsVersion` 防止"旧页面上的批准被绑定到新约束"。
- 后果：历史完整（修复 RA-B06）；重复点击产生的重复 approve 无害；不依赖 Convex 运行时的哈希 API。偏离 F03.7（patch）、RA（contentHash）。

### ADR-09 执行在最后一票的事务里；变更单即执行记录
- 背景：执行落点与 operationId 生成规则未定义（F08.4）；RA 建议独立 executions 表。
- 决定：`executeInTx` 只被 `decide` 调用；主防线是 run 状态守卫，`operationKey = exec:{proposalId}:{cv}` 为第二道保险兼审计键；`changeOrders` 承担执行记录（含 decisionIds、规则与模板版本），承诺带执行时预算快照；执行后 cv +1。
- 后果：不存在悬空的"已全员批准未执行"；没有可被重放的执行入口；少一张表。偏离 RA（executions 表、重发执行按钮）。

### ADR-10 约束变化 → 旧 run 取代 + 新 run；不复制提案
- 背景：F04.1 的两种写法（同一 run 回到 negotiating / 取代 + 新 run）不能同时成立；RA-R11 的 revalidated 复制被否决。
- 决定：取代 + 新 run；新 run 的起始状态由"当前提案在新约束下是否仍通过"和"是否存在全局可行组合"决定（09 §9.4）；只有被取代的 run 原本非终态时才开新 run。
- 后果：每个 run 的 cv 固定，回合守卫简单；条款不变时同一提案重新审批；执行后的约束变化不会自动花钱调用模型。

### ADR-11 自建编排，重试只在应用层一层
- 背景：F10.3 的三个选项；F10.4 指出多层重试相乘；inputs/04 §2 的组件事实。
- 决定：自建（scheduler + 回合表 + 看门狗）；SDK `maxRetries: 0`、`timeout: 90 s`；应用层每回合最多 2 次自动尝试 + 3 次人工重试。
- 后果：每次 HTTP 尝试一行用量记录，成本可精确追溯；无组件确定性约束；全局并发控制留作扩展（workpool）。偏离 F10.4 红队建议（自建路线 SDK `maxRetries: 2`）。
