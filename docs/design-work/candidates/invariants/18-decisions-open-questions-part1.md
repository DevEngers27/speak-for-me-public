# 18 决策记录与开放问题 · part1：ADR-01 至 ADR-10

> 格式：背景 / 选项 / 决定 / 后果。凡与原 README（01）或 Role A 分支（03）或审查建议（02）不同之处都在此记录。

## ADR-01 不变量优先 + 房间聚合写锁（M-ROOM）
- **背景**：Convex 无唯一约束、无行锁；正确性依赖"单一写入口 + 先查后写 + OCC"（inputs/04 §1.6）。索引区间读是否进入 OCC 读集待验证。
- **选项**：A 每个唯一性各自依赖索引区间冲突；B 所有房间内业务 mutation 都 patch `rooms`（至少 eventSeq），使同房间写入必然冲突串行。
- **决定**：B，并把 56 条不变量逐条落到"表字段 + 唯一写者 + 守卫"（02）。
- **后果**：同房间吞吐受限（本产品可接受）；唯一性守卫不依赖待验证的平台细节；`ops.auditRoom` 作为运行时第二道防线。

## ADR-02 预算是 finance 简报的规则字段
- **背景**：原 schema 把预算放在全员可见的 rooms 上（GAP-01）；审查建议独立 `budgets` + `budgetChanges` 表（F02.4）；Role A 建议"budget 实体或 finance 简报字段"。
- **选项**：A rooms 字段；B 独立 budgets 表；C finance 简报的结构化规则字段。
- **决定**：C。预算上限与外部已承诺随 finance 的 briefVersions 版本化，变更原因写在版本上。
- **后果**：约束变化只有一条路径（`commitBriefVersion`），不可能"改了预算忘了 bump"；预算历史即 finance 版本历史；预算披露复用通用披露机制。代价：`updateBudgetCap` 需要以最新版本为底构造新版本（便捷入口已提供）。

## ADR-03 约束版本是一个实体（约束集），执行也会递增
- **背景**：原方案只有 `rooms.constraintsVersion` 计数器，递增点未定义（F09.1 blocker）；Role A 只在改上限时递增（RA-B02）。
- **选项**：A 计数器 + 各处手动递增；B 约束集表，记录各角色确认版本指针与已承诺快照，唯一写者 `bumpConstraints`。
- **决定**：B；递增点 = 规则字段变化的简报确认 + 执行（09 §2）。
- **后果**：任一提案在任一历史版本下的评估可复现；"为什么旧审批失效"可解释；执行后开始的新 run 自动以新的已承诺为基线。

## ADR-04 已承诺 = finance 声明的外部已承诺 + 本系统台账
- **背景**：原方案 `rooms.committedCents` 与 commitments 两份真相（F02.3）；审查建议在台账里写一条 simulated baseline。
- **选项**：A 存量计数器；B 台账含 baseline 行；C 外部部分作为 finance 规则字段，台账只记本系统执行。
- **决定**：C。
- **后果**：台账与执行一一对应（EX-4），台账不需要"非执行来源"的写入口；外部已承诺由 finance 本人确认并带模拟标记（GAP-16）；CS-4 把两部分连起来。

## ADR-05 自建编排（mutation + scheduler + 回合表 + watchdog）
- **背景**：scheduled action 至多一次、不重试；组件选项见 inputs/04 §2。
- **选项**：自建；workflow；agent 组件。
- **决定**：自建（10 §1）。agent 组件与已定 SDK 冲突；workflow 的确定性约束与快速迭代冲突；无论哪条路都要自建迟到拒收与私密上下文。
- **后果**：零新依赖；需自写 watchdog 与重试；全部状态可查询。17 记录何时重新评估。

## ADR-06 提案完全不可变，状态全部派生；不存内容哈希
- **背景**：审查建议 proposals 存 status（active/superseded/executed）与 validation 快照（F03.6）；Role A 建议 contentHash。
- **选项**：A 存 status；B 只存不可变条款与创建时结论，状态由指针与执行表派生；哈希可选。
- **决定**：B，且不存哈希（不可变 + 绑定 proposalId 已等价于绑定内容）；`contentKey` 仅用于展示与去重。
- **后果**：提案表成为纯只追加表（PR-1 可由门面机械保证）；不会出现状态与指针漂移；展示需要一次派生计算（成本可忽略）。

## ADR-07 可行集不进入代理上下文
- **背景**：审查建议"代码枚举候选、模型在候选中挑选"以缩短提示、降低延迟（F05.5、F06.5）。
- **选项**：A 把可行集给所有代理；B 只给每个代理"其委托人可见数据"可推出的东西，可行集仅用于预检、用尽处理与测试。
- **决定**：B。可行集是预算、截止日等私密约束的派生值；给 provider 代理就等于经由 rationale 把余量透露给 provider（违反 BR-4 派生闭包）。
- **后果**：代理可能多走一两轮（受 maxRounds 与调用预算约束）；用尽时由 customer 在代码给出的可行包中选择（choose_package），不会卡死；隐私由构造保证。

## ADR-08 跨方没有模型自由文本；clarify 变成向字段所有者本人的披露请求
- **背景**：原契约 `publicSummary` 是必填自由文本（GAP-06）；Role A 允许带标注与数字检查的 `agentExplanation`；审查要求公开文本模板化（F05.3）、clarify 由谁回答未定（GAP-11）。
- **选项**：A 模型写公开解释 + 数字扫描；B 公开文本全部模板化，模型文本只给本方；clarify 由被问方代理回答 / 由被问方本人决定披露。
- **决定**：B；clarify → disclosure 请求，由字段所有者本人决定是否披露、对谁披露。
- **后果**：没有代理对代理的注入通道；没有"代理替委托人披露"的可能（核心 1 的严格形式）；代价是跨方说服力有限，由结构化动作与模板承担。

## ADR-09 决定只追加；拒绝立即重启协商；只能撤回批准
- **背景**：审查建议同 (proposal, user) 只保留最新决定并 patch（F08.1）；Role A 建议只追加 decisions 并允许 withdraw；Role A 的拒绝是死路（RA-B16）。
- **选项**：A patch 最新决定；B 只追加，最新者生效。拒绝后：A 停在 needs_input；B 立即 superseded + 新 run。
- **决定**：只追加（核心 6）；拒绝必须带原因码并立即启动新 run（trigger human_reject）；withdraw 只针对批准、执行前有效。
- **后果**：完整审批史可审计（含 stale_reject 显示）；拒绝永远有出路；误拒不能撤回（界面二次确认）。

## ADR-10 约束变化：旧 run 终止 + 新 run；仍可执行的待批提案不迁移；不复制提案
- **背景**：审查内部两种写法冲突（F04.1 整理者注）；Role A 在仍可行时复制出 revalidated 新版本（RA-R11）。
- **选项**：A 同一 run 回到 negotiating；B 旧 run superseded + 新 run；对仍可执行的提案：复制新版本 / 原样保留。
- **决定**：B；仍可执行时 run 不迁移、提案不复制，只要求在新约束版本上重新批准。
- **后果**：持久化守卫只需比较 run 的约束版本（CS-5）；run 成为"一组约束下的一次协商"的自然单位；版本表没有条款相同的噪音行。
