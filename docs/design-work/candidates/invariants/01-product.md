# 01 产品：用户、首个场景、做什么与不做什么、关键旅程

## 1. 用户与角色

| 概念 | 含义 |
| --- | --- |
| 用户（user） | 一个 Clerk 账号。可以在不同房间担任不同角色 |
| 参与方 / 席位（participant） | 某用户在某房间中的唯一角色。一人一房一席，一角色一席（ID-3、ID-4） |
| 角色（roleKey） | 由场景声明。首个场景：customer（项目负责人）、provider（服务商）、finance（预算负责人） |
| 房主（owner） | 建房的用户；只能邀请、改名、关闭房间，不因此获得审批或读取他人简报的权力（ID-7） |
| 代理（agent） | 每个角色一个，只为其委托人工作；看到的数据 = 委托人能看到的 + 委托人自己的简报（RN-6） |

目标用户（V-02）：中型企业中的项目负责人与预算负责人，以及与之合作的外部服务商。组织形态是待验证的假设（14 §1）。

## 2. 首个场景

软件服务范围变更：customer 提出变更请求（若干请求项、必需项、截止日），provider 为每项报价（可有多个变体），finance 持有预算上限与系统外已承诺金额。三方的代理协商出"包含哪些项、用哪个变体、哪天交付"；代码计算金额并校验预算、必需项、日期与来源；三方对具体版本审批；最后一票原子写入变更单、预算承诺与任务。审批途中预算下调时，旧方案自动失效，系统重谈或向具体的人请求取舍（14）。

## 3. 系统做什么

1. 私密委托：每方填写结构化约束、软偏好与私密备注，逐字段决定对谁披露（07 §3）。
2. 代理协商：provider 代理提议，customer 与 finance 代理评估、还价或提问；动作全部结构化（05）。
3. 确定性校验：预算、必需项、截止日、报价来源与有效期、金额求和全部由纯函数完成（06）。
4. 版本化审批：人对 (不可变提案, 约束版本) 审批；任何规则输入变化都让旧审批不再计数（08）。
5. 原子执行：最后一票在同一事务写入变更单、承诺、任务，幂等（08 §4）。
6. 约束变化恢复：即时阻断、自动重谈；无解时向能解决的人并行发出具体取舍请求（09）。
7. 追溯：每个结果都能从事件、约束集与不可变记录还原来历（09 §9）。
8. 诚实标注：模拟数据、stub 代理、代理建议、估算成本都有标记（SIM-1）。

## 4. v1 范围

| 进入 v1 | 不进入 v1（见 17） |
| --- | --- |
| 引擎 + scope_change 场景插件 | 第二个场景（接口已就绪） |
| Clerk 登录、邀请链接、一人一席 | 邮件通知、成员移除、房主转移、一席多人 |
| 结构化简报、逐字段披露、版本历史 | 自由文本"共享声明"、按字段的代理授权 |
| 从粘贴文本抽取简报草稿（需本人确认） | PDF 解析 |
| 三方代理（llm / stub 两种模式） | 多模型、调用点级模型选择（待用户决定） |
| 人工取舍请求、披露请求、choose_package | 审批有效期 |
| 变更单页面与打印视图 | CSV 导出、外部集成、修订已执行变更单 |
| 用量与估算成本显示、调用预算 | 跨房间共享预算 |
| 响应式网页（含手机上的审批与请求） | 原生移动应用 |

明确永不做（核心 7）：转账、电子签名、修改外部 ERP、宣称端到端加密或"零泄露"。

## 5. LLM 做什么、代码做什么（回答"为什么需要三个代理"，F01.1）

| 工作 | 谁做 | 说明 |
| --- | --- | --- |
| 金额、预算、日期、必需项、来源、可行性枚举 | 代码 | 06；模型输出中没有金额字段 |
| 是否需要人来决定、问谁、给哪些选项 | 代码 | 05 part2 §2、06 §9 |
| 在委托人的软偏好与私密备注下选择方案、提出还价、决定何时提问 | 代理 | 这些信息是非结构化的（"报表的自定义筛选是加分项"） |
| 向委托人解释"我为什么这么做" | 代理 | rationale，只给委托人 |
| 把混乱输入（邮件、需求描述）整理成待确认的结构化草稿 | 代理 | 抽取，必须本人确认 |
| 批准 | 人 | 代理的"建议接受"永远不是批准 |

finance 代理不做算术（代码已做），它为 finance 本人解释提案对预算的影响并给出建议（ADR-16）。产品文案如实描述这一分工。

## 6. 关键用户旅程

**J1 建房与邀请（customer）**：登录 → `/rooms` 新建（标题、目标、时区、我的角色 customer）→ 设置页为 provider、finance 生成邀请链接（各显示一次）→ 通过邮件或聊天发出。对方打开 `/invite/{token}` → 登录 → "Join as Service provider"。

**J2 填写与确认简报（三方各自）**：customer 列请求项、勾选必需、填截止日（默认不披露）；provider 为每项报价、可加便宜变体、确认"被提案引用的报价行会公开"；finance 填上限与外部已承诺，看到"披露给 customer"已预选并决定是否保留。确认前看到"他方能看到什么"的真实预览。三方都确认后房间进入 ready。

**J3 协商与审批**：任一方点 "Start negotiation" → 工作台显示 "Provider agent drafting…" → 规则阻断的方案带原因出现在版本表 → 有效方案出现，customer 与 finance 代理给出建议（标注"advice"）→ 各方在提案卡上看到条款、检查、执行预览，点击 "Accept terms of v2" / "Approve budget commitment for v2"。

**J4 预算下调与恢复（核心转折）**：finance 在简报页把上限改为 $4,800 并填写原因 → 三个窗口同时看到 v2 被阻断（finance、customer 看到差额，provider 只看到"超出 finance 限额"）与各自的旧批准变为 stale → 新一轮协商自动开始 → 新方案 v3（$750）出现 → 三方重新批准 → 变更单 CO-0001 写入。

**J5 无解时的取舍（变体 tradeoff）**：预算下调后没有可行方案 → 系统不调模型，直接向 customer（"把报表改为可延后？"）、finance（"把上限提到 $4,900 以容纳 v2？"）、provider（"修订报价？"）并行发出请求 → 第一个改变约束的回答生效，其余自动关闭 → 新一轮协商；若三人都拒绝，run 以 no_agreement 结束，系统如实显示"当前约束下没有一致意见"。

**J6 结果与追溯**：结果页显示变更单（执行前后预算快照按权限显示）、任务（provider 可更新状态）、完整审批记录（含失效的旧批准）、时间线（可按版本筛选）、"我的代理"面板中的 rationale。

**J7 失败与重试**：模型超时或输出不合法时自动重试一次；仍失败则 run 显示 "Failed — Retry turn"，任一方可重试；迟到的结果不会覆盖更新的状态。
