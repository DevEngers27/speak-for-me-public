# 01 产品

## 1.1 一句话

Speak for Me 是一个多方 AI 协商工作台：每个参与方把目标、硬约束和偏好私密地交给自己的 AI 代理；代理只在**代码已确认可行**的方案之间协商并给出建议；人批准一个具体版本；全部必需审批到齐后系统原子地写入内部执行记录；任何约束变化都会让旧方案与旧审批自动失效，并触发重新协商或向具体的人请求取舍。

差异化是这条完整链条——私密委托 → 代理协商 → 代码校验 → 人批准具体版本 → 原子写入 → 约束变化后的失效与恢复——而不是"两个代理对话"（V-01、V-08）。

## 1.2 用户与角色

| 角色 | 典型身份 | 交给自己代理的私密输入 | 在系统里能做的事 |
| --- | --- | --- | --- |
| customer（项目负责人） | 客户方的产品 / 项目负责人 | 请求范围、必需项、重要项、截止日、首选日期、备注 | 写简报、选择披露、接受条款、拒绝、回答请求 |
| provider（服务提供方） | 外包工作室、供应商（通常属于另一家公司，V-02） | 交付偏好、产能等备注；**报价目录一经确认即公开** | 确认目录、手动提出候选、接受条款、更新任务 |
| finance（预算负责人） | 客户方财务 | 预算上限（默认对 customer 披露）、已承诺额基线、备注 | 调整上限、记录基线、批准预算承诺 |
| 房间创建者 | 以上任一人 | — | 邀请、撤销邀请、关闭房间（不带来额外审批权） |
| 运维 | 部署方 | — | 只经 CLI：seed、熔断重置、调整上限、整房间删除 |

**假设（需验证，F01.4、17 §17.6）**：首个场景假定"外包工作室 + 有独立预算负责人的中型客户"或企业内部采购；小企业里 finance 常由项目负责人兼任——系统允许同一个人担任不同房间的不同角色，但在一个房间里一人只能占一个角色。服务方愿意进入客户的工作区是一个待验证的采用假设。

## 1.3 首个场景：软件服务范围变更

客户要在已有合同之外增加 SSO 登录、月度报表、数据导出三项工作；总预算 $5,000，已承诺 $4,000；全量变更（含加急）$1,400 超预算且晚于截止日；一期（登录 + 报表，加急）$900，承诺后 $4,900。审批途中 finance 把上限降到 $4,800：$4,900 的方案立刻被阻断、已有审批失效，系统在新约束下重新协商出 $800 的标准交付方案（恰好等于余量），三方重新批准后写入变更单、预算承诺与任务。完整走查见 14 §14.9；无可行方案、预算低于已承诺、代理故障等路径见 14 §14.10。全部示例数据标注为模拟（核心 8）。

## 1.4 为什么需要 LLM 代理（以及它们不做什么，F01.1）

| 由代码完成 | 由代理（模型）完成 | 由人完成 |
| --- | --- | --- |
| 权限、算术、硬约束校验、可行组合枚举、状态迁移、何时必须问人、问题与选项的生成、对他方可见的全部文本 | 在可行候选之间按本方的软偏好与备注做取舍；以固定理由码表达偏好；在必要时提出一个封闭的澄清问题；给委托人写简短的私密理由；（可选）把粘贴的文字抽成待确认的草稿 | 确认简报与披露、确认报价、调整预算、回答请求、批准 / 拒绝 / 撤回、手动提出候选 |

如果模型完全不可用，系统仍然可以从头走到执行：提议方的人从候选中手动选择，其余流程不变（R9）。这既是可靠性设计，也是对"代理只建议"的结构性保证。

## 1.5 系统做什么 / 不做什么

**做**：房间与邀请；结构化私密简报与逐字段披露；版本化报价目录；约束版本与快照；代码枚举候选与确定性校验；三方代理协商（有界轮次、可重试、可恢复）；版本化审批（区分条款与预算承诺）；原子幂等执行（变更单、预算承诺、任务）；约束变化后的自动失效、重新审批、重谈或问人；完整可追溯的历史；模型用量与估算成本；stub 模式与故障注入。

**不做**（核心 7 与范围纪律）：转账、付款、电子签名、具有法律效力的合同、修改外部 ERP（只留 outbox 扩展点，17 §17.3）；端到端加密或"零泄露"承诺（P-11）；token 级流式聊天；代理之间的自由文本对话；把未经人确认的抽取结果当作约束；代理市场、语音、原生移动端。

## 1.6 关键用户旅程

| # | 旅程 | 要点 |
| --- | --- | --- |
| J1 | customer 建房并邀请 provider、finance | 选择场景与自己的角色；为其余角色生成单次邀请链接；对方登录后加入 |
| J2 | 三方写私密简报 | 结构化字段 + 私密备注；逐字段选择谁能看到；侧栏实时显示"别人能看到什么"；确认时接受委托条款 |
| J3 | provider 确认报价目录 | 为请求范围的每一项确认价格与交付日期，另可确认加急费；确认即公开 |
| J4 | 开始协商并审批 | 就绪后任一人点击开始；回合进度实时可见；提案卡显示条款、检查、批准后将创建的记录；三方各自批准 |
| J5 | 预算在审批途中被下调 | finance 预览影响后确认；三个窗口同时看到阻断与旧审批失效；系统自动在新约束下重谈；新版本重新审批后执行 |
| J6 | 无可行方案 | 不调模型；系统向能解除阻断的人分别发出具体的取舍请求（提高上限 / 降价 / 放宽必需项）；第一个约束变化后自动重谈；都拒绝时明确显示"无法达成一致" |
| J7 | 代理故障 | 回合自动重试；仍失败时任何人可重试，provider 可手动选择候选；评审方代理失败不阻塞审批 |
| J8 | 结果与追溯 | 变更单（内部记录，非合同）、任务、审批记录（含失效与撤回）、约束历史；从变更单一路追溯到决定、提案、报价版本与约束版本 |

## 1.7 产品原则

1. 默认展示结论、阻断与需要你做的决定；代理活动可展开（V-11）。
2. 每个按钮都说清它批准的是哪个版本、在哪个约束版本下；代理的建议永远标注 "advisory"。
3. 模拟、种子、stub、录制的内容在数据与界面上都有标注（核心 8）。
4. 对他方可见的内容永远来自显式披露与模板，不来自模型自由发挥。
5. 不在产品界面写演示脚本文案。

## 1.8 有用性度量（V-14、AC-14）

得到首个有效提案的时间、人工干预次数（请求、手动提案、恢复）、硬约束违规拦截数、协商受阻次数、每次执行的模型估算成本；全部报告样本量与失败，未测量前不陈述改进幅度（15 §15.4）。
