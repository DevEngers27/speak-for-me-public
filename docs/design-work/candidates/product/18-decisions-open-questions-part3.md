# 18 决策记录与开放问题（part3）：ADR-19～ADR-27、输入冲突裁决、开放问题、待验证

## ADR-19 事件：结构化 payload + 受众 + 读时渲染

- **背景**：原 events 二元可见性、自由 summary（GAP-15、DM-08）；Role A 的 action 自由字符串、预渲染文本、客户端过滤（RA-B20）；审查多数主张事件全房间可见、私密细节放按角色控制的表，红队指出口径不一（F07.6）。
- **决定**：`events.data` 是按 `type` 判别的联合，payload 不含私密值与自由文本；受众 `room | seats`，几乎都是 room；私密细节（请求选项、rationale、被阻断原因）不做成事件；排序字段用 `v.commitTs()`（待验证，回退 `_creationTime`）。
- **后果**：时间线可安全地对全房间开放；同一事件按查看者渲染；调试需要的细节在 `turns`、`humanRequests` 中按席位读取。

## ADR-20 软约束不递增约束版本

- **背景**：审查未细分（F09.1 改写要求明确）；Role A 无软约束字段。
- **决定**：偏好字段、备注、共享说明、披露变化不递增约束版本、不使签核失效、不自动开 run。
- **后果**：避免无意义重签；按新偏好重谈需手动 `requestRun`。

## ADR-21 人可以直接从候选提出提案

- **背景**：Role A 的 "Check confirmed options" 让任何人随时触发规则选择器（被否决）；但模型不可用或卡住时，流程不能停（核心 2：代理只建议）。
- **决定**：具备 `proposal.author` 能力的席位可在候选浏览器中选择本人作用域内的候选生成人提出的提案（可同时接受）；进行中的 run 会被取消；被阻断尝试计入有界推断披露的频率限制。
- **后果**：`AGENTS_DISABLED`、模型拒答、额度用尽时仍能完成全流程；finance 无此能力（它的职责是批准预算而不是选范围）。

## ADR-22 seed 不直接写中间状态（Role A Q11）

- **决定**：seed 与变体都经与真实用户相同的引擎写入路径；"v2 待批"之类阶段通过 stub 模式真实运行得到；预置结果标注来源。
- **后果**：fixture 永远满足全部不变量；排练每次新建房间，旧房间保留。

## ADR-23 必需项不能被"显式延后"而仍算合法

- **背景**：审查中 P4 原文允许"⊆ scope 或显式标 deferred"，整理者建议不允许（F06.2）。
- **决定**：`required_items` 检查要求必需项全部包含；想延后必需项，customer 必须先把它改为非必需（规则字段 → 约束变化），取舍请求里提供这一选项。
- **后果**：延后必需项一定是 customer 本人的显式决定，并留下简报版本记录。

## ADR-24 界面语言

- **决定**：v1 产品界面英文；全部用户可见句子来自按 locale 组织的模板，读时渲染；设计文档中文（任务书）。
- **后果**：加入 zh-CN 不改数据；优先级为开放问题。

## ADR-25 clarify 的回答是人的披露决定

- **背景**：GAP-11（clarify 由谁回答）；审查要求升级由代码决定（F05.6）；核心 1 要求对他方可见内容经显式披露决定。
- **选项**：A 被问方代理据其简报自动回答；B 生成给被问方本人的 `disclosure` 请求，回答即修改披露设置。
- **决定**：B。话题由插件声明并映射到具体字段；同一约束版本内被拒的话题不再问。
- **后果**：代理永远不会替人披露；代价是一次 clarify 会让 run 以 `needs_input` 结束、等人回答后再开新 run。

## ADR-26 报价在 provider 确认时公开（Role A Q4、GAP-26）

- **选项**：A 报价私密直到被提案引用；B 确认即对房间公开。
- **决定**：B。现实中报价就是发给客户看的；provider 的私密底线用简报字段（最低金额、备注）表达。确认对话框明确提示。
- **后果**：候选与提案的金额都是公开信息，模板可以放心展示；"被引用才公开"的隐式披露不再存在。

## ADR-27 后续变更在同一房间进行（Role A RA-S05、GAP-13）

- **决定**：执行后房间进入 `executed`；"Start a follow-up change"（`requestRun`）在同一房间开新 run，版本号接续、台账累积；修订已执行的变更单不在 v1（17）。
- **后果**：一个项目的变更历史集中在一个房间；与原 README "修订开始新流程并保留历史"一致。

## 18.1 输入之间冲突的裁决（按任务书第 3 节）

| 冲突 | 来源 | 裁决 | 依据 |
| --- | --- | --- | --- |
| 签核：patch 为最新 vs 只追加 | 审查 F03.7 vs Role A RA-D12 | 只追加（ADR-08） | 核心 6 |
| 预算：独立 budgets 表 vs finance 约束对象 | 审查 F02.4 vs Role A RA-D02 | finance 简报规则字段 + 台账（ADR-04） | 简单：少一表一入口 |
| 上限低于已承诺：needs_input vs 拒绝 | 审查 F06.3 vs Role A RA-R10 | 拒绝（ADR-16） | 核心 7、I-9 |
| 约束变化：新 run vs 原 run 回到 negotiating | 审查内部（F04.1 整理者注） | 新 run（ADR-07） | 可追溯、守卫简单 |
| 绑定：contentHash vs termsKey | Role A vs 审查 F03.7 | termsKey（规范化字符串）；哈希待 `crypto.subtle` 验证后再议 | 平台不确定性 |
| 事件可见性：全房间 vs 受众联合 | 审查多数 vs Role A RA-D15 | 受众联合但几乎都用 room，私密细节不做成事件（ADR-19） | 两者兼顾 |
| customer 是否见预算数字 | 审查 F07.1（推荐可见）vs Role A（他方只见结论） | 默认披露给 customer，finance 可改（ADR-12） | 核心 1：显式披露决定 |
| priority 放目录还是 customer 简报 | 审查 P4 vs architecture-09 | customer 简报（必需项） | 必需与否是 customer 的判断 |

## 18.3 待验证的平台事实（实现前做最小实验，结论回填）

1. Convex 打包器能否跟随 `convex/` 以外的相对导入（`../engine`、`../scenarios`）。
2. `v.commitTs()` / `ctx.db.vars.commitTs` 的实际用法与索引排序。
3. 公共函数 `returns` 校验器是否拒绝多余字段。
4. mutation 中 `crypto.getRandomValues` / `crypto.subtle` 是否可用且适合安全用途。
5. 默认运行时 `Intl.DateTimeFormat` 的 `timeZone` 支持；query 中 `Date.now()` 与结果缓存的交互。
6. OCC：索引区间读在并发插入时是否冲突；持续冲突的重试次数与报错形态（04 #2）。
7. convex-test 0.0.65 的身份模拟、调度推进 API 与局限（04 #14）。
8. Claude 结构化输出：根级 `anyOf`、`enum` 保留、可选属性、schema 编译延迟与缓存（04 #6）。
9. `@anthropic-ai/sdk` 1.1.0 在默认运行时的打包与长请求行为（04 #4）；Opus 5.5 回合 p50/p95（04 #5）。
10. `fallbacks` 与 `output_config.format` 能否同用（04 #7）；action 最长运行时间（04 #1）。
11. Clerk：Convex JWT 是否带 name/email；Restricted 注册在免费版是否可用；生产实例是否需自有域名；原生集成 vs JWT 模板（04 #13）。
12. `npx convex env default set` 对已有 deployment 是否生效；Convex 备份/导出与日志流能力。
