# 18 决策记录与开放问题（part2）：ADR-10～ADR-18

## ADR-10 提出方排序 + 代码选择；提案只在全部检查通过时创建

- **背景**：原草案由模型给出 `additionalCostCents`（PR-05）；Role A 的 `bestFeasibleOption`（条目最多再最便宜）直接充当协商结果并忽略必需项与截止日（RA-R12、RA-B12）；审查要求可行组合由代码枚举（F06.5）。另有隐私约束：给 provider 代理"全局可行集合"会泄露 finance 的预算区间。
- **选项**：A 模型自由给出条款；B 代码给全局可行候选让模型挑；C 模型在**本方作用域视图**的候选中排序（1–5 个），代码用完整视图选第一个可执行者，失败时一次 a2 再试，仍失败转为偏好请求。
- **决定**：C。金额、日期、来源由 `toTerms` 计算；提案创建前全部检查必须通过（I-14）。
- **后果**：显示给人的每个提案在创建时都可执行；模型发明不了金额；单次调用即可完成"排序 + 选择"。代价：被阻断候选的结论回给提出方，构成有界推断披露（ADR-13）。

## ADR-11 对他方可见的文本只由模板生成

- **背景**：原 `publicSummary` 是必填自由文本、无长度上限（GAP-06、F05.3）；Role A 已全部用模板（RA-T01）但写入时预渲染为英文（RA-T02）。
- **选项**：A 模型写公开摘要 + 正则扫描金额；B 模型写、人审后公开；C 公共文本只由模板从结构化字段读时渲染，模型 rationale 只给本方。
- **决定**：C。事件与提案只存结构化数据；同一事件按查看者渲染不同措辞；唯一跨席位的自由文本是人亲自写并选择披露的共享说明，进入他方代理时位于不可信定界块。
- **后果**：主泄露路径（代理说出自己委托人的私密值）被结构性关闭；跨代理注入通道关闭；可本地化。代价：代理无法向他方"说服"，只能以动作（候选、原因码）表达立场——这正是"代理只建议、人决定"想要的。

## ADR-12 披露模型：逐字段披露 + 检查结论基线 + 按查看者投影

- **背景**：原 `shareableFacts: string[]`（RO-13）；Role A 每条 shared 布尔、受众只有全房间（RA-D06），且全量状态发到浏览器再过滤（RA-D16 否决）；审查推荐预算按买方/卖方划分（F07.1）。
- **选项**：A 预算对全员公开；B 完全隐藏，连阻断原因都不说；C 逐字段披露（受众：全房间或指定角色）+ "每个检查的通过/失败与原因码对全体可见"的基线 + 服务端按查看者投影。
- **决定**：C。scope_change 默认：必需项 → 全房间；截止日、偏好日、最低金额 → 私密；预算上限与已承诺 → customer。检查参数（数字）只给能看到全部输入的人。
- **后果**：provider 能知道"超预算"但不知道多少（F07.1 的最小披露）；投影是唯一防线，靠 `returns` 校验器与金丝雀测试守护。

## ADR-13 有界推断披露

- **背景**：任何"是否可执行"的信号都是私密约束的函数；系统必须解释阻断，又要限制可推断的信息量。
- **选项**：A 不给任何信号（无法协商）；B 给全局可行集合（泄露区间）；C 只在必要渠道给逐候选结论，并设上界与频率限制。
- **决定**：C（07 第 7.6 节列出全部渠道与上界）。
- **后果**：推断风险被量化并写入披露基线；finance 可选择主动披露以减少来回。query 形态的 `feasibleAfter` 预览无法限频，作为已接受风险记录。

## ADR-14 人工请求是完整实体，且同时发给多人

- **背景**：原文只有 `needs_input` 状态与 clarify 动作，没有对象、选项与回答的结构（GAP-11、GAP-12、F02.7）；审查给出完整版与 `optionGroupId` 轻量版；Role A 的三种取舍对应三种权限（RA-R13），开放问题 Q8 问同时发还是顺序发。
- **选项**：A 轻量版（候选提案共用 optionGroupId）；B `humanRequests` 实体，kind ∈ {tradeoff, preference, disclosure}，选项是可执行的意图。
- **决定**：B；一组取舍请求同时发给所有有可行动选项的角色，任何一方造成的约束变化关闭整组并重新预检。
- **后果**：每个"卡住"都有具体的人与具体动作；请求绑定约束版本，约束一变就 superseded。比 A 多一张表，但可追溯、可取消，且承载了披露请求（ADR-25）。

## ADR-15 执行：最后签核的同一事务；`executions` 即变更单

- **背景**：原 schema 没有变更单表（GAP-02）；幂等落点与 operationId 生成方式未定义（AX-04）；Role A 的"最后一票即执行"与服务端派生 operationId 方向正确（RA-R07、RA-R08）。
- **选项**：A 签核齐全后由调度任务或按钮执行；B 在完成最后签核的 mutation 内执行，`operationKey = exec:{proposalId}:{constraintsVersion}`；变更单另设表或与执行记录合一。
- **决定**：B；执行记录与变更单一一对应，合为 `executions`；执行递增约束版本并关闭协商（`negotiationOpen = false`）。
- **后果**：没有"已全签未执行"的悬空状态，也不需要"重试执行"入口；状态守卫为主、operationKey 为辅；执行前后的台账写入快照，不再用减法推算（修 RA-B09）。

## ADR-16 预算上限不得低于已承诺

- **背景**：审查建议总额低于已承诺时进入 needs_input（F06.3）；Role A 直接拒绝（RA-R10）。
- **选项**：A 允许写入并进入 needs_input；B 拒绝写入（`CAP_BELOW_COMMITTED`）。
- **决定**：B。
- **后果**：不变量"台账 ≤ 上限"始终成立（I-9）；已承诺不能在系统内撤销（核心 7），现实中的超支属于系统外的财务处理。错误消息中的已承诺金额只对 finance 显示。

## ADR-17 模型调用规范

- **背景**：平台约束：采样参数、prefill、强制 tool_choice 会 400；Opus 5.5 thinking 常开、计入 max_tokens；`zodOutputFormat` 会丢 enum；`messages.parse()` 解析失败抛错并丢 usage；默认超时与重试远超 action 上限（04 §4）。技能规定默认 `claude-opus-5-5`，不得自行降级。
- **决定**：默认 `claude-opus-5-5`、显式 `effort: medium`（抽取 `low`）、`max_tokens` 6,000；`messages.create` + 自建 JSON Schema（保留候选键 enum，联合放在 `move` 属性内）+ `stop_reason` 分支 + Zod 严格校验 + 语义校验；SDK `timeout 60s`、`maxRetries 1`，应用层自动重试 1 次；每回合无状态重建上下文，system 与本方简报设缓存断点；不开服务端 fallbacks（待验证兼容性后再议）。
- **后果**：换模型时请求形状不变；任何失败都先保存用量；是否把某些调用点换成 Sonnet/Haiku 是用户决策（开放问题）。

## ADR-18 finance 代理保留顾问型模型调用

- **背景**：finance 的"检查支出"与确定性校验重叠（F01.1、F10.17）。
- **选项**：A finance 无模型调用，纯规则；B 保留一次审阅回合，只解释与建议，不做算术。
- **决定**：B，并在产品文字中如实描述为"顾问型"。stub 模式下 finance 恒为接受。
- **后果**：finance 本人得到"预算还剩多少、为什么建议批准"的解释；多一次并行调用，延迟不增加串行深度。若评测显示价值低，可改为 A（开放问题）。
