# 00 概览（part1）：是什么、文档地图、设计原则、核心保证、主要差异

> 本份设计（candidates/product）的主视角是**三种角色的真实旅程**与**引擎 / 场景插件的边界**：先写 customer、provider、finance 从进入房间到看到执行结果的完整体验（01），再定义插件接口并用第二场景检验（06），由此推导数据模型、状态机、协议、权限、API 与前端。part2 是术语表与阅读路线。

## 0.1 一句话

Speak for Me 是一个多方 AI 协商工作台：每方把目标与约束私密地交给只为自己服务的代理；代码枚举并校验可行方案，代理在可行方案中按各自委托人的偏好排序、还价、请人披露或请人亲自选择；人对"提案 × 约束版本"签核；签核齐全时同一事务写入内部变更单、预算承诺与任务；约束一变，旧签核自动过期、旧方案按需阻断，并自动重新协商或向具体的人请求取舍。

## 0.3 设计原则

1. **代码决定事实，代理表达判断**：金额、日期、来源、可行性、权限、版本、执行全部由确定性代码完成；代理只在代码给出的可行空间里按自由文本偏好排序与表达立场（01 第 1.4 节）。
2. **私密是结构，不是界面**：服务端按查看者投影；对他方可见的文本只由模板生成；代理看到的永远等于其主人能看到的（07）。
3. **人批准的是一个不可变对象**：提案只追加，签核绑定 `proposalId + constraintsVersion + termsKey`（08）。
4. **一个入口改一个事实**：约束版本只经 `bumpConstraints`；房间每个可变字段有唯一写入口；每条"逻辑唯一"有唯一写入口 mutation（03 第 3.21–3.22 节）。
5. **能派生的不存储**：可执行性、签核状态、房间阶段、已承诺金额都读时计算（I-10）。
6. **每个卡住都有人和下一步**：无解、需披露、需偏好、模型失败，都落到具体席位的具体动作（04 第 4.9 节、X6）。
7. **引擎不懂场景名词**：插件是声明 + 纯函数；加场景不改引擎（06）。
8. **反对过度设计**：每个组件写明解决的问题；两个方案都完整时选简单的（不引入 workflow 组件、DSL、多包仓库、额外数据库）。

## 0.4 不可动摇的核心如何被保证

| # | 核心（任务书第 3 节） | 保证它的设计点 |
| --- | --- | --- |
| 1 | 私密委托 | 简报草稿与版本只对本席位可读（03 第 3.7–3.8 节）；逐字段披露 + 接受邀请时同意的披露基线（07 第 7.2、7.4 节）；每个 query 按查看者投影并声明 `returns`（7.5）；代理上下文唯一入口 `getTurnInput` 显式白名单（7.7）；有界推断披露（7.6、ADR-13）；金丝雀测试（16 第 16.3 节） |
| 2 | 代理只建议 | 代理输出只有五个结构化动作，`recommend_accept` 永不写 `decisions`（I-18）；签核唯一入口是人的 `decisions.record` / `requests.answer`；界面"advisory"标注；代理不能替人披露（ADR-25）；人可直接从候选提出（ADR-21） |
| 3 | 人批准具体版本 | 提案不可变（I-11）；签核绑定提案 + 约束版本 + `termsKey`，客户端必须回传期望值（08 第 8.1 节）；约束或条款变化即 stale（04 第 4.6 节）；插件规则升级也递增约束版本（03 第 3.24 节） |
| 4 | 代码负责校验 | 校验管线与四步模型输出校验（06 第 6.2 节、05 第 5.5 节）；金额与日期由 `toTerms` 从已确认清单计算，`terms_consistent` 防篡改（6.5）；提案只在全部检查通过时创建（I-14）；签核与执行在事务内重算（08 第 8.7 节） |
| 5 | 执行幂等且原子 | 最后签核的同一 mutation 内执行 17 步（08 第 8.7 节）；状态守卫 + `operationKey` 双防线；签核区间读触发 OCC；真实部署并发脚本（16 第 16.4 节） |
| 6 | 历史不可篡改 | 简报版本、约束修订（含 `inForce`）、提案、签核、执行、回合、事件只追加；清单版本化；`replayRuleView` 可重建任一版本（09 第 9.9 节） |
| 7 | 执行边界 | 执行只写内部表，执行模块禁止导入外部客户端（I-22、11 第 11.4 节）；外部集成只经 outbox 扩展点（17）；界面固定声明"内部记录，非付款、非签署" |
| 8 | 不伪造 | `isSimulated` 整房标注、stub 代理 `agentMode`、fixture 来源徽章（13 第 13.9 节）；seed 不直接写中间状态（ADR-22）；无解由代码判定后向人请求，不伪造一致（09 第 9.6 节）；代理笔记没有就空着 |

## 0.5 与原方案的主要差异（详见 18 的 ADR）

| 主题 | 原 README / Role A | 本设计 |
| --- | --- | --- |
| 场景 | 全局 role enum、预算在 rooms 上 | 引擎 + 插件，角色、字段、清单、规则由插件声明（ADR-01） |
| 预算 | rooms 上全员可见的两个字段；可累加计数器 | finance 简报规则字段 + 台账求和；默认只披露给 customer（ADR-04、ADR-12） |
| 范围与价格来源 | 自由字符串 `scope`/`sourceRefs`，模型给金额 | 两份版本化共享清单；模型只排序候选键；代码算金额（ADR-03、ADR-10） |
| 状态 | 一个 `status` 七个值 | 房间 open/closed + run + 提案 + 签核 + 请求分层，阶段派生（ADR-07） |
| 签核 | 版本号绑定、可改的 `approvalRequired` | 只追加 decisions、terms/budget 两类、快照必需签核人（ADR-08） |
| 约束变化 | 只有改上限递增；复制 revalidated 版本 | 所有规则输入都递增；不复制提案（ADR-09） |
| 公共文本 | 自由文本 `publicSummary` / 写入时预渲染 | 模板读时渲染，rationale 只给本方（ADR-11） |
| 人工介入 | 只有 needs_input 状态 / 静态提示 | `humanRequests` 三种请求，同时点名具体的人（ADR-14、ADR-25） |
| 执行 | 无变更单表 / 重发执行按钮 | `executions` 即变更单，最后签核同事务执行（ADR-15） |
| 编排 | 未定 | 自建 scheduler 链 + 看门狗（ADR-06） |
| 读模型 | Role A 全量状态发浏览器 | 按查看者投影的 DTO（ADR-12） |
