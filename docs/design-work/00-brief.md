## 1. 我们在做什么

Speak for Me 是一个多方 AI 协商工作台：每个参与方（第一个场景里是客户 customer、服务提供方 provider、财务 finance）把自己的目标、硬约束和偏好私密地交给自己的 AI 代理；代理之间就一件需要三方同意的事（第一个场景：软件服务的范围变更，含范围、报价、交付日期）协商出方案；代码独立校验预算、必需范围、日期和来源；人类对一个具体版本做审批；全部必需审批到齐后系统原子地、幂等地写入内部执行记录（变更单、预算承诺、任务）；任何约束变化（例如预算下调）都让旧方案和旧审批自动失效并触发重新协商或向具体的人请求取舍。

原项目是 Cal Hacks 2026 的黑客松仓库（/Users/zhennn/cal-hack-2026-main，只读）。它的 README 把上述想法写得很清楚，但代码只有 236 行骨架，计划被 24 小时截止时间和四个赞助商赛道扭曲。**现在的决定：把原仓库和另一份本机分支只当作想法输入，不受任何截止时间与赛道约束，重新设计并从零实现一个完善的系统。**

## 3. 不可动摇的核心（设计必须保证）

1. **私密委托**：每个参与方的私密简报只有本人和为本人服务的代理可见；任何对他方可见的内容都经过显式的披露决定。不得把私密字段发到浏览器再隐藏。
2. **代理只建议**：代理可以提议、还价、澄清、建议接受、拒绝；代理的"建议接受"永远不是人的批准。
3. **人批准具体版本**：审批绑定不可变的提案内容和当时的约束版本；条款或约束变了必须重新审批。
4. **代码负责校验**：权限、算术、硬约束、状态迁移、来源核对由确定性代码完成，不信任模型声明；价格、范围项、日期只能来自用户确认过的信息，模型不得发明金额。
5. **执行幂等且原子**：全部必需审批到齐后，一次事务写入执行记录；重复点击、并发、重试不得产生重复承诺或任务。
6. **历史不可篡改**：提案只追加不修改；旧审批、旧提案、约束变更历史全部保留；可从事件追溯每个结果是怎么来的。
7. **执行边界**：系统只写内部记录，不转账、不签署有法律效力的合同、不改外部 ERP；外部集成是后续扩展点。
8. **不伪造**：任何模拟数据、预置数据、录制结果都要在数据和界面上标注；缺信息时向人请求，不编造一致意见。

## 6. 写作与质量要求

- 具体，不要口号。表结构写出字段与类型（TypeScript / Convex validator 语法），状态机写成迁移表，消息写成 Zod schema，权限写成矩阵，关键流程写成分步时序（谁调用什么函数、读写哪些表、哪一步会失败、失败后状态是什么）。
- 每个重要决定都写：目标、决定、理由、被否决的备选及原因、带来的不变量、开放问题。
- 保持一致：03 的字段、04 的状态、05 的消息、07 的矩阵、12 的函数必须互相对得上；同一个概念全篇一个名字。
- 不受截止时间约束，但反对过度设计：每个组件都要说明它解决什么问题；两个方案都完整时选简单的。
- 平台事实以 inputs/04 为准；不确定的 API 行为标注"待验证"，不要编造。
- 文件写入规则：所有产出只写到 WS 下属于自己的目录；单次 Write 不超过 12,000 字符，长章节拆成 NN-slug-part1.md、part2.md；不要在最终回复里粘贴文档正文。
