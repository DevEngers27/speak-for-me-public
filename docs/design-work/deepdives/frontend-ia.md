## 1. 目标与范围

### 1.1 目标

1. **私密投影是唯一防线**：浏览器拿到的每一个字节都来自已按查看者裁剪的 Convex query 返回值（核心 1）。前端不存在"取回再隐藏"的代码路径，也不需要任何"这个字段别显示"的判断。
2. **默认展示结论、阻断和需要你做的决定**：每个角色进房第一眼看到"等你做什么"、当前提案能否执行及原因、谁还没批准。
3. **版本意识**：用户在任何时刻都知道自己面前是哪个提案版本、哪个约束版本；批准按钮上写着版本号；旧审批显示为"不再适用"而不是消失（核心 3、6）。
4. **人与代理的边界在视觉上不可混淆**：代理的建议（recommend_accept 等）与人的决定在不同区域、不同组件、不同文案中呈现；代理建议永远不出现在审批面板里（核心 2）。
5. **约束变化即时可见**：预算一提交，三个角色的窗口在同一次订阅推送中翻转为"阻断"，不等模型；重新协商随后异步出现（F09.3、F13.1）。
6. **诚实**：模拟数据、stub 回合、种子记录都有标签；没有代理消息就显示为空，不编造（核心 8）。
7. **可访问**：键盘可达、屏幕阅读器能听到禁用原因与实时变化、不只靠颜色表达状态。

### 1.2 范围

在范围内：
- Next.js App Router 的页面与路由、页面壳与客户端岛的划分；
- 每个页面订阅哪些 query、每个 query 的返回形状（视图模型）和按角色的差异；
- 实时更新策略（订阅拓扑、一致快照、版本偏斜处理）；
- 加载 / 错误 / 空状态 / 断线状态；
- 人工取舍请求（humanRequest）的交互；
- 预算或其他约束变更时的呈现；
- 审批的版本显示与"代理建议 ≠ 批准"的呈现；
- 组件清单、可访问性要点；
- 对 Role A 分支四个页面的吸收与否决。

不在范围内（由其他专题负责，本文只引用接口）：
- 表结构与字段的最终命名（03）；状态值的最终集合与迁移守卫（04）；
- 公共文本模板的具体措辞来源与 reasonCode 全集（05、06）；
- 字段 × 角色披露矩阵的最终裁决（07）。本文按 F07.1 推荐方案（买方 customer + finance 可见预算数字，provider 只见结论）写示例，并把"谁可见预算数字"做成场景配置项，07 改裁决时前端不改结构；
- 审批 kind、执行事务（08）；约束版本递增点（09）；run 生命周期（10）。

### 1.3 术语（本文用到的前端术语）

| 术语 | 含义 |
| --- | --- |
| 视图模型（view model） | 某个 query 为某个查看者返回的、已裁剪的 DTO。前端只渲染视图模型。 |
| 页面壳（shell） | Server Component，只负责布局、静态文案和把路由参数传给客户端岛；不取任何房间数据。 |
| 客户端岛（island） | `"use client"` 组件，内部用 `useQuery` 订阅视图模型。 |
| 待办（todo） | 服务端为当前查看者算出的"等你做"的事项，带 kind 与相关 id。 |
| 版本偏斜（version skew） | 同一页面上两个 query 的结果来自不同的 constraintsVersion。 |
| 翻转（flip） | 约束变更提交后，提案可执行性、审批有效性、待办在所有窗口同时改变。 |

## 2. 决定与理由

每条决定格式：目标 → 决定 → 理由 → 被否决的备选 → 带来的不变量 → 开放问题。

### D-FE-01 页面壳 + 客户端订阅，v1 不做服务端预取

- **目标**：首屏可用、实时、无私密泄露面。
- **决定**：所有 `app/` 下页面是 Server Component 壳，只渲染布局与路由参数；所有房间数据在客户端岛中通过 `useQuery` 订阅。v1 不使用 `preloadQuery`。
- **理由**：`preloadQuery` 需要在 Server Component 里 `await auth()` 取 Convex token、再把 `Preloaded` 传入客户端，增加一条认证路径和一类"token 模板不匹配"故障；收益只是首屏少一次骨架闪烁。两种方式的私密性相同（都必须来自已投影 query），所以选简单的。
- **否决**：(a) Server Component 用 `fetchQuery` 渲染静态快照：失去实时性，翻转不会出现；(b) 预取 + 续订：留作性能优化，接口不变（同一个 query），见 §7 待验证 #9。
- **不变量**：I-FE-1 Server Component 不向客户端组件传递任何从 Convex 取得的数据（props 会进入 RSC payload）。
- **开放问题**：若后续开启 `cacheComponents`，需确认用户相关数据不会被缓存（04 待验证 #17）。

### D-FE-02 一个聚合的工作台 query 承载所有"随约束版本变化"的数据

- **目标**：预算变更后三个窗口同一刻翻转，同一窗口内不出现"提案已阻断但审批仍显示有效"的混合状态。
- **决定**：`rooms.view({ roomId })` 一次返回：房间头、阶段、待办、当前提案卡、提案历史（有界）、审批面板、预算视图、run 状态摘要、我的 open 人工请求、共享事实、参与方状态、最近一次约束变更摘要。凡是依赖 `constraintsVersion` 计算的字段只出现在这一个 query 中。大而增长的列表（事件时间线、代理协商记录）拆成独立的分页 query，它们不含可执行性判断。
- **理由**：单个 query 在服务端是一次一致的读快照，天然保证同窗口一致；Convex 客户端把同一时刻的多个 query 更新放在一条 Transition 消息里一起应用（`convex/src/browser/sync/client.ts:467-471`），但跨 query 的一致性是否是正式保证待验证（§7 #1），所以关键判断不依赖它。
- **否决**：(a) 每个面板各自一个 query：版本偏斜风险，且每个 query 都要重复鉴权与投影；(b) 整份房间状态一个 query 含事件与协商记录：任何一条代理消息都会让整个工作台重算、重渲染，且返回体无界。
- **不变量**：I-FE-2 `isExecutable`、审批行状态、待办、预算结论只由 `rooms.view` 计算；其他 query 返回的对象若需要显示状态，只带 `constraintsVersion` 标记，不重复计算。
- **开放问题**：rooms.view 的读集较大，任何房间写入都会让全部订阅者重算。v1 房间规模（3 人、提案 ≤ 数十个）下可接受；需在 15 中加 query 耗时指标。

### D-FE-03 视图模型按查看者投影，返回形状用 `returns` validator 锁死

- **目标**：把"不得把私密字段发到浏览器"变成可机械检查的约束。
- **决定**：每个公开 query 声明 `returns`；对角色敏感的部分用判别联合表达，而不是"可选字段"。例如预算视图是 `{ visibility: "amounts", ... } | { visibility: "verdict", ... }`，provider 收到的对象在类型上就没有金额字段。投影由纯函数 `projectRoomView(input, viewer)` 完成（frontend-ia/projection.ts），query handler 只做鉴权、读表、调用投影。
- **理由**：判别联合让"provider 收到金额"在类型层面不可表达；`returns` 校验若拒绝多余字段（待验证 §7 #2），开发者误 spread 文档会在运行时直接失败，而不是静默泄露。纯函数投影可以脱离 Convex 单测（16 的隐私金丝雀）。
- **否决**：(a) 一个大对象 + `v.optional` 金额字段：类型上允许误填，审查时难发现；(b) 按角色写三个 query：重复代码，三份投影容易漂移。
- **不变量**：I-FE-3 任何公开 query 的 handler 不得 `return doc` 或 `...doc`；只能返回投影函数构造的新对象。I-FE-4 provider 的任何视图模型中不存在 cap、committed、totalAfter、headroom、shortfall 这些字段，也不存在能与已知报价相减反推出已承诺额的总数（F07.1 文案陷阱）。

### D-FE-04 待办由服务端按查看者计算，前端只负责排序与链接

- **目标**：Role A 的"Decisions needed from you"保留，但不在浏览器里用全量状态现算。
- **决定**：`rooms.view` 返回 `todos: TodoView[]`，每项 `{ kind, priority, refs }`；`rooms.listMine` 返回每间房的待办数与最高优先级 kind。前端根据 kind 与 refs 生成链接和文案（frontend-ia/copy.ts）。服务端不返回 URL。
- **理由**：待办依赖他方状态（例如"你的旧审批已失效"依赖约束版本），只有服务端拥有完整数据；URL 是前端关注点。
- **不变量**：I-FE-5 待办列表为空时，界面显示"现在没有需要你做的事"，并说明在等谁（等待对象只显示角色，不显示原因细节）。

### D-FE-05 审批调用携带"我看到的版本"，服务端拒绝过期视图

- **目标**：人批准的就是屏幕上那个版本在那个约束版本下的内容（核心 3）。
- **决定**：审批、拒绝、回答人工请求、确认简报、更新预算这五类改变结果的 mutation 都接受 `expectedConstraintsVersion`（审批再加 `proposalId`）。服务端在约束版本不一致时抛 `ConvexError({ code: "STALE_VIEW" })`，前端显示"约束刚刚变化，请重新查看后再决定"并保持在当前页面。
- **理由**：订阅推送与用户点击之间存在竞态：finance 降预算的那一刻 customer 可能正好点下"Accept terms of v2"。没有这个参数，服务端会把这次点击记成对新约束版本的批准，或者记成对旧版本的批准但用户以为有效。携带版本让竞态变成一个可解释的错误。
- **否决**：只靠服务端读当前版本：无法区分"用户看到的是哪个版本"。
- **不变量**：I-FE-6 前端提交的版本号只能取自同一个 `rooms.view` 结果，不能来自本地缓存或 URL。
- **接口**：08 的 `decide` 与 12 的签名需要包含这两个参数（§6）。

### D-FE-06 不做乐观更新；关键操作在断线时禁用

- **决定**：审批、执行、预算、简报确认、回答请求不使用 `withOptimisticUpdate`，以订阅回推为准；按钮在调用期间显示进行中并防重复点击（服务端仍需幂等，F08.4）。`useConvexConnectionState()` 显示未连接时，上述按钮设为 `aria-disabled` 并写明"正在重新连接"。草稿编辑（简报草稿、抽取复核）允许本地状态，自动保存失败时显示未保存提示。
- **理由**：Convex 客户端会在重连后重发在途 mutation（04 §1.11），对审批来说这意味着用户离线时点的批准可能在约束已变化后才到达；有 D-FE-05 兜底，但禁用更易理解。乐观更新会短暂显示"已批准"，与"以服务端结果为准"冲突（04 §5 含义 4）。
